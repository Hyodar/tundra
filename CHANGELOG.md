`## Unreleased` holds the next release's notes, one grouped note under `###` sections.
`scripts/release.py cut X.Y.Z` renames it `## X.Y.Z - <date>` and opens an empty one; the
`vX.Y.Z` tag's release body is that section, and a tag without one is refused

## Unreleased

tundravm v2 makes mkosi accessible for confidential VMs by making the choices: Debian
trixie, systemd, a measured UKI, Intel TDX. You declare one Python `Image`, the compiler
writes one plain mkosi 27.1 tree, and thirteen commands take it to a locked, reproducible,
signed build that runs, deploys and attests. No compatibility alias is kept. The attested
endpoint has run simulated under QEMU only; no real TDX quote is recorded yet.

### SDK

- **Breaking:** `Image`, `Service`, `Component` and `Profile` replace `Recipe`, `Variant` and `Fragment`, and `profile` replaces `variant` everywhere, `--json` and `tundravm.testing` included.
- **Breaking:** every public name has one home (`tundravm`, `.ports`, `.systemd`, `.components`, `.storage`, `.secrets`, `.sources`, `.errors`, `.testing`), each shipped component lives in its own submodule (`tundravm.components.tee`, `.network`, `.access`, `.container`, `.observability`) while `tundravm.components` keeps the API for writing one, and flat imports are gone.
- **Breaking:** the API speaks the public model (`Resolved.targets`, `.components`, `.production`, `class X(Component, name=)`, `ImageFile.component`), and the internal-model test helpers and fixtures are gone.
- **Breaking:** `Image(volumes=, secrets=)` are gone, since the image collects each volume and secret from what binds it.
- **Breaking:** `tundravm.bake` is `tundravm.build`, the command's verb, and its directory keyword is `into=` (was `build=`).
- `Image` implies the TEE baseline, a curated kernel, a firewall that opens only exposed ports (and 8745 where the attested endpoint listens), one hardened user per service and `tdxs`, from a shipped library of `TeeBase`, `Network`, `Firewall`, `Tdxs`, `SshAccess`, `DevAccess`, `Observability` and `Container`.
- `Image(sysctl={"vm.max_map_count": 2097152})` writes kernel parameters to `/etc/sysctl.d/60-<name>.conf` and refuses a key `TeeBase`'s hardening sets.
- **Breaking:** a relative host path (`File.copy(src, ...)`, `Tree(src, ...)`, `Kernel.build(config=, patches=)`, `AptRepository(key=Path(...))`, and a `Local` or `File` path a component's `compose()` writes) is beside the file that declares it, as `Local` is, not the working directory, so a build reads the same files from any directory.
- An image file imports modules from its own directory and its project's (the nearest `pyproject.toml`) from any working directory, so a project carries its own components, and two projects' image files loaded in one process each import their own.
- `Component` is a dataclass with `compose()`, typed exports and an optional `check()`, and `Profile(extends=, add=, changes=, production=)` edits the image with `value.ref.edit(...)` and `.remove()`.
- **Breaking:** a profile edit sets any `Service` keyword but `name=` and (`readiness=`, `credentials=`, `unit=`, `timer=` and `quotes=` included) and builds what it implies (its probe, credential waits, drop-in, timer and firewall rule and its dependents' ordering), `service.ref.remove()` drops everything the service lowers to, and an edit is refused that binds a credential through argv or `environment=`, builds another binary, gives a volume directory another `user=`, drops a readiness or removes a service another service requires, or requires the `.ready` of a service the image does not declare.
- `Service` takes an argv, `expose=` alone opens a port, `requires=` waits for real readiness (`Notify`, `TcpProbe`, `HttpProbe`, an endpoint, or a setup task's `task.output(path)`, which skips the service when the task wrote nothing), and `quotes=True` joins the `tdx` group and requires the evidence service, refused as `user="root"` or a user named `endpoint`.
- `hardening="python"` names the sandbox per runtime (`static`, `jit`, `node`, `python`, `dotnet`, `relaxed`) and `Hardening.preset(NAME, ...)` a deviation, where `dotnet` allows `AF_NETLINK` (`network="inet+netlink"` for any other preset) and `capabilities=["CAP_SYS_TIME"]` also drops `ProtectClock=` and allows `@clock` back.
- An argv word may be an `int` (`300`) or `TCP(p).address` / `UDP(p).address` (`0.0.0.0:p`), so a port is typed once beside `expose=[port]`, and a refused word's hint lists every kind argv takes.
- An `Endpoint` of another service in argv or `environment=` (which now takes one, rendered as its URL) implies `requires=` on that service's readiness, which `requires-implied` (info) names, and a profile that removes the upstream is refused.
- `Service(description=)` sets `Description=`, which a component's service otherwise takes from the first sentence of the component's docstring, and a `Container`'s units name it (`Container bob`, `SSH into container bob`, `Relay 127.0.0.1:8545 into container bob`).
- A `Service(timer=...)` binds delivered and generated secrets and a volume `state=` as a long-lived service does, so its unit waits for each required secret and the volume's unlock, reads an optional one as empty until it arrives, and writes its volume directory.
- `TcpProbe` and `HttpProbe` read `interval=` as a systemd time span (`"500ms"` by default), as `timeout=` and `Every()` do, refusing a span systemd does not read, zero or `infinity`, and `HttpProbe` refuses a URL that names no host.
- `Service.packaged(unit, package=, hardening=)` runs a Debian package's unit under the image's sandbox, which replaces the package's own, and `convert --from systemd` writes it for drop-ins whose unit is not in the set.
- A list wherever a public value's docs show one type-checks, since `Build(command=, packages=, install=)`, `User(groups=)`, `DropIn`'s lists, `Hardening(devices=, capabilities=, syscalls=)`, `GoBinary(tags=)` and `CargoBinary(features=)` take a `Sequence` and keep a tuple.
- Every image generates a fresh secp256k1 instance key at boot (tmpfs, root-only), and `InstanceKey()` (`tundravm.secrets`) hands it to a service as a credential, while `instance-key-exposed` refuses anything else that names it, `show` says who takes it, and `run status` and `attest` print its public key.
- `Generated(name)` (`tundravm.secrets`) is a secret the image writes at boot for the services that bind it, such as the Engine API JWT an execution client and its consensus client share.
- `Volume` (at `/persistent/<name>`, `unlock=` with no default) takes `OperatorKey`, `TpmSeal` or `BrokerKey`, a `Secret` is a systemd credential bound by naming it in argv or `environment=`, and `state / "output.log"` is a path inside a volume directory, refusing one that leaves it.
- The image takes `AttestedTLS` and `TLS`, `RootFS.verity()` and `RootFS.initramfs(max_size=)`, `Kernel(cmdline=)`, and `Mkosi(settings=, scripts=)`, which writes each key in its mkosi section and refuses one tundravm writes, naming the slot that sets it.
- A `Volume` installs `e2fsprogs` and `mount` beside `cryptsetup`, so `disk-setup` formats with `mkfs.ext4`, which no image had.
- **Breaking:** an image with a secret, an `AttestedTLS` ingress, firewall modes or a volume an operator unlocks runs the attested endpoint (`tundravm-endpoint.service`) instead of `secret-delivery`: its quote binds the nonce, its TLS key, the SSH host keys, the instance public key and each attested TLS certificate key, it writes secrets, passphrases and SSH keys only on the session that fetched that evidence, once per boot, `secrets.ready` waits for the required secrets, and `sshd` waits only for its host keys.
- **Breaking:** a profile's attested endpoint takes, and its boot waits for, only the secrets its own units read, so a development profile whose observability stays in the guest never waits for the export's credential, and `secrets deliver` refuses a name the instance's profile does not read.
- **Breaking:** an `OperatorKey()` volume has one owner, whose first signed write pins its SSH key in the volume's LUKS2 header and in an encrypted copy inside it, after which the endpoint takes credentials, passphrases, mode switches and SSH keys only when that key signs them over the evidence, a volume whose header and copy disagree is closed again, and the dev probe's `volume:` row names the owner, so a reboot no longer hands root to whoever reaches the endpoint first, while `TpmSeal` and `BrokerKey` volumes pin no one.
- **Breaking:** on TDX the attested endpoint takes a delivered SSH key, root's or a `Login`'s, only from an owner an `OperatorKey()` volume's encrypted copy confirmed this boot (unlock, then `attest` again), so an image without such a volume has no delivered SSH on TDX, while a simulated boot takes the first.
- The certificate key of each `AttestedTLS` port is made at boot (`attested-tls-<port>-key.service`) and read by the relay as a credential, and the relay starts only once its upstream is ready.
- **Breaking:** `File(owner=)` and `Tree(owner=)` are applied at boot by the runtime-init step `owners`, which the services wait for, instead of by a tmpfiles file that nothing applied.
- An initramfs-rooted image makes `/` `root:root 0755` before `sysinit.target` (`tundravm-root-mode.service`), where the kernel's rootfs left tmpfs's `1777`, writable by anyone and refused by sshd for every key under `/etc/ssh`.
- `SshAccess(login=Login(name, keys=, owner=, commands={...} | shell=, home=))` lets an account other than root in with its own keys (baked, or a `Secret` the endpoint writes to its `authorized_keys.d` file) or the owner's (`owner=True`), with no password or forwarding, into `login-menu` (`tools/cmd/login-menu`), which lists the commands on an empty request, runs exactly the argv a request names and refuses anything else, while `ssh-login-shell` warns on a production shell and an image's own `SshAccess` joins the control plane's.
- **Breaking:** a `Login` command is `Command(path, word, ...)`, run as the login, or with `sudo=True` as root through exact `sudoers` lines that `visudo -c` checks at build, each word a literal string, `Int("lines", 1, 10000)` or `Choice("mode", "production", "maintenance")`, and the `{name:int:LO-HI}` and `{name:choice:a|b}` words, an argv of one list and a plain list are refused.
- **Breaking:** `Command(..., modes=["maintenance"])` offers a command in those firewall modes only, which `login-menu` reads from the boot's log of switches and `login-mode-undeclared` (error) checks against the image's `Firewall`, and `dev=True` offers it in development builds only, refused in an image with no development profile.
- `Firewall(modes=)` hands a login menu `firewall.status` and `firewall.switch` (`Command(MODE_SWITCH, "to", Choice("mode", *modes), sudo=True)`), so `mode-switch to MODE` switches locally into RTMR3.
- A login's menu gets no terminal (`PermitTTY no`, `restrict` keys) except in a development build of a login with `dev=True` commands, which says `PermitTTY yes` and gives its keys `pty` (the endpoint's `ssh: {pty: true}` for the owner's), so `ssh -t` gets a terminal and `login-menu` passes the client's `TERM`.
- **Breaking:** an image whose `SshAccess` declares a `Login` hands root no delivered key unless `from_delivery=True`, a `Login(owner=True)` takes it instead, and root without a key never logs in (`PermitRootLogin no`).
- sshd bounds unauthenticated connections per source (`PerSourceMaxStartups 4`, `MaxSessions 1`), so a menu login can face the network in every mode.
- A `Login` enables `systemd-user-sessions.service`, so `/run/nologin` no longer turns a non-root login away after boot.
- **Breaking:** an account belongs to one declaration, so a `Container` and a `Login` of one name, a service whose default user is a `Login`'s or a `Container`'s account, and a service run as a `Login`'s account are refused where they silently shared it.
- `Container(name, argv, packages=, files=, state=, user=)` runs a program in a Debian root of its own, the subimage `mkosi.images/<name>/` built from the image's snapshot and shipped in the measured payload as `/usr/lib/tundravm/containers/<name>.raw`, under `RootImage=` with its own user and network namespace, refusing an OCI reference, and the manifest records each root's sha256 under `containers`.
- A `Container` with `expose=`, `egress=`, `modes=` or `serves=` gets the veth `ve-<name>`: each exposed TCP or UDP port is DNATed to it (in one mode only when a firewall mode names it), it sends exactly what `egress=` names and what `modes={"maintenance": Egress(...)}` adds in one mode, the metadata servers refused without `metadata=True`, and `serves=[TCP(8551)]` with `probe=TcpProbe(8551)` gives a host service `container.endpoint(8551)` at the veth address only.
- **Breaking:** `Container(requires=[nethermind.rpc])` relays a host loopback endpoint into the container's namespace at the same address, through a relay named after the export, `<container>-<component>-<property>` (`bob-nethermind-rpc.socket`), not its port, and cut with a hash past 32 characters.
- **Breaking:** `Container(ssh=ContainerSsh(port=, owner=True))`, or `keys=`, runs the container's own sshd, letting its user in by key alone, on a host key the host makes each boot that every quote binds under the container's name and `attest` pins for `ssh -p PORT`, and `Mode(ingress=[searcher.ssh])` opens it by name.
- A container's user is an account of its own, its uid pinned from its name and written into its root's `passwd`, and `argv` may be left out when sshd is the program.
- **Breaking:** a `Container` runs in a PID namespace of its own (`PrivatePIDs=yes`, `ProtectProc=invisible`), so the tenant neither lists nor signals a host process, and writes group-readable files (`UMask=0027`), which a host service reads by joining `container.group` instead of running as its uid.
- **Breaking:** `Container(binds=[Bind(path, at=, writable=, file=)])` shows host paths read-only unless `writable=True`, refusing the control plane under `/run/tundravm`, the kernel's interfaces and whole system trees, and `Bind(data.directory("input"), writable=True)` keeps the directory's service as owner, gives it the container's group (`2750`, or `2770` writable, setgid so what either writes there is the group's) and makes the container wait for its volume.
- `Service(logs=data.directory("app-logs"))` keeps a service's logs on a volume (`$LOGS_DIRECTORY`), written group-readable (`UMask=0027`), so a container's read-only `Bind` of the directory reads them; `runtime=` refuses a volume directory.
- A `group=` directory one service binds is `<service>:<group>`, written group-readable (`UMask=0027`), and may name a `Login`'s own group.
- `Container(hardening=)` takes a `Service`'s sandbox levels (`"static"` by default, `"jit"` for a runtime that writes code), while sshd's sandbox stays tundravm's.
- A built kernel of an image with a `Container` asks for `CONFIG_BLK_DEV_LOOP=y` and `CONFIG_EROFS_FS=y`, Debian's kernel gets `<name>-loop.service`, which runs `modprobe loop` with `CAP_SYS_MODULE` alone and no network, and a networked container takes its `ip_forward` from a `sysctl.d` line (`60-container-<name>.conf`) and its namespace from `<name>-net.service`, which runs `ip` with `CAP_NET_ADMIN` and `CAP_SYS_ADMIN`, netlink alone and a system call filter.
- **Breaking:** `Tdxs(issuer=)` is gone, since a development profile ships the `simulator` issuer beside the real one and takes it where the execution gate finds no TDX, so a dev build attests `simulated` under QEMU, while a production profile ships the real issuer only.
- **Breaking:** `Network(egress=Egress(...))` drops every outbound packet but the baseline's NTS time and resolvers and what each component's `outbound()` names, and `Service(egress=Egress(...))` accepts more for that service's user alone (`meta skuid`).
- **Breaking:** `Component.outbound()` says where a component sends, which a filtered output chain accepts in each profile that holds it from the component's users alone, a rule per user (its services', or the daemon's that `Component.senders()` names, such as `_chrony` and `systemd-resolve`, and DHCP from `systemd-network`'s), so a component that sends with no sender is refused, while the image's `Egress` and a mode's stay every process's.
- **Breaking:** the cloud metadata servers (169.254.169.254, `fd20:ce::254`, Azure's wire server) take only tundravm's cloud glue and a service declaring `Egress(metadata=True)`, filtered image or not, so no other process fetches the identity token, and naming one in `Egress(hosts=)` or an image-wide `metadata=True` is refused.
- **Breaking:** a host name in `Egress(hosts=)` (`"logs.example:443"`) opens its port only to the name's nftables sets (`host4_NAME`, `host6_NAME`), which `egress-resolve` fills over DNS over TLS once the network is online and every 30s after (`egress-resolve.timer`), so a name is unreachable until it first resolves and keeps its last addresses while it does not, and a service whose own egress names a host starts after the first resolution.
- The NTS servers, `Tdxs`' Intel hosts and the observability sinks take the same path, the DNS-over-TLS resolvers stay literal addresses, and NTP on UDP 123 goes to any address the NTS key exchange names, from chrony's user (`_chrony`) alone.
- **Breaking:** `Host(name, addresses, port=, aliases=)` in `Egress(hosts=)` pins a peer, so the firewall accepts exactly those addresses on that port and the name resolves to them in `/etc/hosts`, the image's or a container root's (which `Container(files=)` may no longer write), and an image pins a name once, never also as `"NAME:PORT"`.
- `Egress(deny=[...])` drops what it names (the entries of `hosts=`, a `Host` at every port of its addresses) ahead of every accept of its chain, the output chain's, a mode's or a container's forward rules, so `Egress(ports=[TCP(443)], deny=[TX_STREAM])` reaches the web but never that peer; a `"NAME:PORT"` there or an entry `hosts=` also names is refused, and `show` lists each drop as a `deny` row.
- **Breaking:** `TeeBase` resolves through `systemd-resolved` over strict DNS over TLS (`DNSOverTLS=yes`, `DNSSEC=no`, no fallback, LLMNR or mDNS) instead of a plain `/etc/resolv.conf`, `Network(dns=["ADDRESS#TLS-NAME"])` names the resolvers (Cloudflare's pair by default, `TeeBase(nameservers=)` gone), and the firewall accepts TCP 853 to them and no plain DNS.
- `Firewall(modes={"production": Mode(), "maintenance": Mode(ingress=[TCP(22)], lasts="30m")})` makes the firewall switchable, so a port a mode names opens in that mode only, the image boots into `production`, a window closes itself on boot time, and SSH in `production`, a mode named `tdx` or `simulated` and `lasts=` on `production` are refused.
- **Breaking:** `PrometheusRemoteWrite(export=)` is the keep-list of series names and presets that leave the TEE (`write_relabel_configs` drops the rest), `health` when neither it nor a rule is given, and every keep-list carries the image's identity (`tundravm_image_digest`, the UKI's Authenticode SHA-384 with the image's name, `tundravm_image_rtmr` and `tundravm_mode`), while `observability-export-unset` refuses a production profile that writes to a `url=` with neither.
- **Breaking:** `PrometheusRemoteWrite(rules=[RecordingRule(record, expr, export=)])` computes series in the guest, so an image ships derived booleans in place of raw series: Prometheus then runs in server mode with its HTTP API on `127.0.0.1:9090` refusing every request (basic auth whose bcrypt hash no password was hashed to), the rules' group carries the image's name, a record needs a colon, `promtool check rules` checks each at build, `export=False` keeps an intermediate series in the guest, and `export=` refuses a rule's record.
- Every series `PrometheusRemoteWrite` sends carries `instance=` the boot's instance key (the public key `attest` prints as bound to the quote) in place of `127.0.0.1:9100`, read from `/run/tundravm/instance-key.env`, so two replicas of one image no longer merge at the sink, and the probe's `observability:series` row checks the label.
- A `Service`'s and a `Container`'s `.metrics` (`active`, `cpu_seconds`, `memory_bytes`, `oom_kills`) and a `Volume`'s (`available`, `size`, `used_ratio`) are PromQL selectors with the unit or mount filled in, so a rule reads `f"max({searcher.metrics.active})"` and `data.metrics.available.over("128Gi")` compares bytes with a binary size.
- **Breaking:** `JournalExport()` and `PrometheusRemoteWrite()` ship to a receiver in the guest (`journal-sink`, Debian's `systemd-journal-remote`, and `metrics-sink`, Prometheus's remote-write receiver, both on the loopback) without `url=`, and in a development profile even with one, the credential unbound and the firewall opening nothing for the sinks, so nothing leaves a dev VM, while a sink on the loopback stays as declared and a production profile reports `observability-sink-unset` until `url=` names the deployment's receiver.

- `PrometheusRemoteWrite(credential=SigV4(region, Secret))` signs each write with the AWS shared credentials file the secret holds (`AWS_SHARED_CREDENTIALS_FILE`, the metadata server never asked), for Amazon Managed Prometheus.
- **Breaking:** every UKI boots with `TeeBase`'s CPU mitigations, `mitigations=auto,nosmt spec_store_bypass_disable=on`, before what `Kernel(cmdline=)` appends, so a parameter that turns a mitigation off (`nospectre_v2`, `mitigations=off`, `mds=off` and their kin) is refused and a repeated one is `kernel-cmdline-repeated`.
- **Breaking:** `Kernel.build(base=DebianConfig("6.12.113-1"), fragments=[Path | KernelFragment(...)], patches=[Path | KernelPatch(...)], hardening=True, modules=False)` compiles, in the image, the stable release a Debian `linux-config` package carries, from gregkh/linux, merging Tundra's hardening first (about 160 options with a reason each), and the declarative `KernelHardening` is gone.
- In a built kernel a fragment that sets a hardening option itself wins, `hardening=False` is the `kernel-unhardened` error in a production profile and a warning in a development one, `config=Path(...)` is hardened too, and the build fails, keeping its configs, when a driver a target needs is not `=y` or a denied option is on.
- `Component.kernel()` returns the `KernelFragment` and `KernelPatch` values a built kernel needs, merged after the kernel's own in declaration order, beside `RootFS.verity()`'s dm-verity, erofs and overlay options and a `gcp` target's BadAML ACPI sandbox patch, and a component a `Profile` adds may ask for none, since every profile boots one kernel.
- The GCP glue names NVMe disks as Google does, sets the hostname, routes forwarded IPs and no longer points `/etc/resolv.conf` at the metadata server (`gcp-metadata-dns.service` is gone), and the Azure glue installs the `curl` its ready report needs.
- Every image powers off in order, since the debloat keeps `poweroff.target`, `reboot.target`, their services and the `shutdown`, `umount` and `final` targets, and `tundravm-power-button.service` (acpid on the ACPI `button` driver) runs `systemctl poweroff` on the power button, so a cloud stop unmounts volumes instead of cutting power.
- **Breaking:** every error is one shape in the image file's words, naming the public object and keyword in what is wrong (`Service("app"): argv= is empty`) before a `fix:` line, a misspelt keyword, a missing argument or a positional too many is a `ValidationError` with the closest keyword, and two services exposing one port or sharing a name are refused.
- `tundravm.testing` holds `plan`, the asserts, `FakeMkosi`, `FakeSources`, `boot`, `assert_probe`, `run_cli` and `FakeEndpoint`, which plays the endpoint, presenting each listener's certificate, with the `relay`, `replay`, `wrong-key`, `wrong-certificate` and `service-quote` misbehaviours.
- A `group=` volume directory is setgid (`2750` by default, the bit added to any `mode=`), so a file written there belongs to the group whoever writes it.

### CLI

- **Breaking:** tundravm has thirteen commands, `new`, `check`, `lock`, `build`, `show`, `run`, `dev`, `deploy`, `attest`, `secrets`, `verify`, `convert` and `doctor`, and with no arguments it prints the first four, `doctor`, `new`, `check` and `dev`, and points at `--help`.
- **Breaking:** `new NAME [--ci]` writes stage 1 of the attested node, its tests and `pyproject.toml` and nothing else (the `minimal`, `service`, `cloud` and `prover` templates and `--template` are gone), and its printed loop, README, tests and workflow run as written, `ruff format` clean, ending at `tundravm dev`.
- `new --ci` writes `.github/workflows/image.yml` (was `tundravm.yml`), whose every push checks `uv.lock`, the image, the lock and the committed tree, then builds the production profile and uploads its manifest, measurements and SBOM, and whose `v*` tag rebuilds that build on a second runner with `verify --rebuild`, attests the provenance of every released file and releases the image, the manifest, `measurements.json`, the SBOM and `SHA256SUMS`, naming `gh attestation verify` only where the attestation ran.
- `doctor` prints one row per capability, then a `fix:` block with the one command that clears each row (`sudo apt install qemu-system-x86 ovmf`, the user-namespace sysctl, the cloud login), in `--json` too, where `build:go` never blocks and names the image's Go sources and `verify:qemu` says what a build predicts.
- `dev [IMAGE]` is the inner loop as one verb: `build --dev` when the image, the lock or a `Local` source's content changed since the latest development build (saying which, else reusing that build), then `run --mode simulated --probe` and the console until Ctrl-C stops the instance, while `--no-follow` returns after the probe.
- `dev` and `run --mode simulated` ask for QEMU and OVMF before anything builds, naming every missing apt package in one command.
- `run --mode simulated|tdx` is explicit, a production build boots fail-closed without TDX, and `run --probe` and `run probe INSTANCE` read the boot probe every development profile carries, write `probe.json` and exit 1 on a failed check.
- Ctrl-C or SIGTERM stops the instance `dev` or `run` follows, even when a script started the command as an `&` job, which inherits SIGINT ignored, and SIGTERM no longer leaves QEMU running.
- A local instance's QEMU monitor listens in `$XDG_RUNTIME_DIR/tundravm` (else `/tmp/tundravm-<uid>`, refused unless only you can enter it), named in the receipt, so a deeply nested project can start one.
- `run` forwards, `deploy`'s firewall line names, and `deploy status` probes 8745 only where the image's firewall opens it.
- The boot probe checks the command line's mitigations (`cmdline`), DNS over TLS (`dns`), `/` against `rootfs=` (`root`, `rootfs:initramfs`, `rootfs:verity`), each egress host's addresses and each user's reach to the metadata server (`egress:HOST`, `egress:metadata:`), each `AttestedTLS` certificate against the evidence (`attested-tls:`), each login (`login:`, `menu:`, `ssh:root`), each container (`container:<name>` with its `:egress`, `:endpoint:`, `:serves:` and `:udp:` rows, `container-ssh:<name>`) and the firewall mode against RTMR3 (`mode:firewall`), and its `service:` failure names a capability the unit was denied.
- A probe that skipped rows as `locked` runs again once the volume opens (`tundravm-probe-again.service`, after the volume's step and the services on it), its first line `tundravm-probe: again: ...`, so `run probe` after `secrets unlock` waits for that run and `probe.json` holds its verdicts and `done` counts.
