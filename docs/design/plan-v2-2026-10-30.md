Date: 2026-10-30. Status: proposal for Franco's review, third iteration (two review passes folded in). Sources: this
repository at `fcc8d8a`; systemd/mkosi at v27.1 (clone `10f43ac`, 110 commits past the tag;
the facts below were checked against the tag); flashbots/flashbots-images at `09c7576`
(2026-10-21); the earlier studies `flashbots-lessons-2026-10-18.md` and
`review-round7-2026-10-18.md`; two research reports and two adversarial review passes (Codex Astra,
high), kept in `docs/design/research-2026-10-30/` (`mkosi-lib-report.md`,
`flashbots-report.md`, `codex-review-1.md`, `codex-review-2.md`). Appendix B lists what the
reviews changed.

## 0. Summary

tundravm does a lot, and that is now the problem. The goal Franco set on 2026-10-18 ("a more
accessible way of using mkosi; really opinionated: mkosi, systemd, Debian") is not what a
newcomer meets: a 101-line starter, 149 public names, 30 CLI verbs with 170 flags, 80 000
words of docs, a `Service` with 43 fields, and a TDX prover that hand-wires twelve concepts
(`Key`, `Disk`, `Secrets`, `RuntimeTools`, `Tdxs(needs=[secrets.ready])`, `SshAccess`,
`Backports`, snapshot and EFI-stub pins, `cryptsetup`, `socat`, ...).

The proposal in one paragraph. **A tundravm image is TDX-capable by construction** and a
production deployment of it requires TDX and fails closed; development runs in an explicit
simulated mode that can never receive production secrets. The user writes an `Image(...)`
with a few keyword slots (`services`, `packages`, `files`, `volumes`, `secrets`, `ingress`,
`components`, `dev`); the TEE baseline, hardening, the evidence service, measured UKI boot
and the inert cloud glue are implied, and **the simplification that matters is automatic
wiring of relationships** (a service names the volume directory and the credential it
needs, and the boot order, units, firewall rules and users follow), not fewer constructor
fields. The compiler emits **one mkosi 27.1 tree that uses mkosi's own composition**
(`mkosi.images/` with the OS as a subimage and the disk wrappers depending on it,
`mkosi.conf.d/`, `mkosi.profiles/dev`), readable by any mkosi user. **mkosi 27.1 is a pinned
dependency** imported and run in-process inside mkosi's own `fork_and_wait`, with its
tools tree (it is not on PyPI and has no API promise, so one version-guarded adapter owns
every import). The CLI becomes **an operator's loop** (`new`, `check`, `lock`, `build`, `show`, `run`,
`deploy`, `attest`, `secrets deliver`, `verify`, `convert`, `doctor`) whose outcomes are
immutable build directories with a signed manifest. The audit stack folds into that
manifest, `build --reproduce` and `verify`.

The runtime contracts a TDX service actually needs (section 6: execution modes, volumes and
their unlock policies, a channel-bound secret-delivery protocol, attested ingress,
per-platform measurement records, the root-filesystem layouts, a tested kernel matrix and
one upgrade path) are specified **before** the convenience API freezes, and the phases
(section 8) are gated on proofs, not on lines deleted. Decisions only Franco can make are in
section 9.

## 2. Principles for v2

1. **TDX-capable by construction, TDX-required in production, simulated only on purpose.**
   Three independent properties. The artifact always carries the supported boot and
   runtime baseline. A production deployment refuses to come up without TDX. A development
   run is `--mode simulated`, with its own credentials and an unmistakable `untrusted`
   verdict; nothing ever falls back silently from TDX to plain QEMU, and simulated or
   debug-enabled evidence never releases production secrets.
2. **Relationships, not fields.** A service names the volume directory, the credential, the
   endpoint and the readiness of what it depends on; the compiler derives units, order,
   users, firewall rules and boot steps. Brevity comes from wiring, not from hiding options.
3. **One opinion per concern, one escape hatch.** Debian trixie, systemd, UKI with
   systemd-stub, networkd, nftables, chrony NTS, hardened services with dedicated users.
   Each concern has one typed declaration and one raw escape (`Mkosi(settings=)`,
   `Unit(text=)`, `DropIn`), both linted, and the escape's resolved effect is recorded so it
   cannot silently contradict an invariant the image advertises.
4. **Name things the way mkosi and systemd name them.** `Image`, `Profile`, `Component`,
   `mkosi.images/`, `[Match]`, `KernelModules=`, credentials. The generated tree must read as
   one a mkosi user would have written, so leaving tundravm is always possible.
5. **The CLI is the operator's loop.** Build, inspect, run, deploy, attest, deliver, upgrade,
   verify. No verb exists because an internal stage does; no needed operation hides behind
   a flag of an unrelated verb.
6. **Delete after proving, never before.** A guarantee moves to its replacement first (boot
   tests, measurement tests, signed manifests), then the old code goes, with no public
   compatibility aliases in between.

## 3. Proposed interfaces

### 3.1 Layer 1: `Image`

The starter, complete (replaces today's 101 lines). A public plaintext service: the
confidential ingress is explicit in the second example.

```python
# demo.py
from tundravm import File, Image, Service, TCP

image = Image(
    "demo",
    packages=["busybox"],
    files=[File.text("/srv/www/index.html", "<h1>demo</h1>\n")],
    services=[
        Service(
            "app",
            ["/usr/bin/busybox", "httpd", "-f", "-p", "8080", "-h", "/srv/www"],
            expose=[TCP(8080)],
        ),
    ],
)
```

Implied, with no further words: Debian trixie from the locked snapshot; the TEE baseline
(today's `TeeBase`) with DHCP, NTS time, a volatile journal, and a firewall that opens
`TCP(8080)` for the app plus the management ingress every image has: the attested endpoint
on :8745 (section 6.3; `run` forwards it, `deploy` records its address and the cloud
firewall rule in the receipt); `app.service` as user `app`, hardened with a tested preset,
restarting on failure; a measured UKI; `tdx_guest`, virtio, NVMe, Hyper-V and gVNIC drivers;
the evidence service on `/run/tdx/quote.sock`; the Azure and GCP provisioning glue, inert
off-platform (`ConditionVirtualization=`). The default artifact is a raw bootable disk for
QEMU; `build --target gcp,azure` adds the cloud packages without changing the payload.

The operator transcript for it, end to end:

```
$ tundravm new demo && cd demo
$ tundravm build                       # lock written, payload.efi + qemu.raw, measurements, manifest
$ tundravm run --mode simulated --dev  # instance demo-1; :8080 and :8745 forwarded; verdict: simulated
$ curl http://127.0.0.1:8080/          # <h1>demo</h1>
$ tundravm run stop demo-1
```

The prover, complete (replaces today's 129 lines):

```python
# prover.py
from tundravm import AttestedTLS, DevAccess, Image, OperatorKey, RootFS, Secret, Volume
from tundravm.components.taiko import Raiko

data = Volume("data", mount="/persistent", unlock=OperatorKey())
jwt = Secret("jwt", rotation="restart")
raiko = Raiko(source="./raiko", state=data.directory("raiko"), jwt=jwt, listen="127.0.0.1:8080")

image = Image(
    "prover",
    components=[raiko],
    volumes=[data],
    secrets=[jwt],
    ingress=[AttestedTLS(443, upstream=raiko.http)],
    rootfs=RootFS.verity(),
    dev=DevAccess(ssh_keys=["~/.ssh/id_ed25519.pub"]),
)
```

`Volume("data", unlock=OperatorKey())` is a LUKS2 volume whose passphrase an operator
supplies over the attested channel on each boot (flashbots' model); `unlock=TpmSeal()` is
the alternative where a vTPM is trusted, with its platform, PCR policy and recovery method
stated (section 6.2). `Secret("jwt")` is a requirement: the value arrives through `tundravm
secrets deliver` (or a broker pulling the same protocol) and the component reads it as a
systemd credential; nothing is written into the image. `Raiko` is a supported workload
contract, not a convenience: the component pins a Raiko revision, its Cargo toolchain and
features, names the RPC and configuration inputs it needs, defines its readiness check and
the smallest proof request the acceptance test sends, and measures its footprint; because
Raiko and its dependencies are large the example selects `rootfs=RootFS.verity()`
explicitly (section 6.6). The caller never names a unit, a port or a path inside it.
`AttestedTLS(443, upstream=raiko.http)` is the only way requests reach the prover.
`DevAccess` takes effect only in the `dev` profile, whose artifacts are marked
non-production.

Its transcript:

```
$ tundravm lock --update raiko                      # pin the Raiko revision and toolchain
$ tundravm build --target gcp                       # payload.efi, qemu.raw, gcp.tar.gz, measurements, manifest
$ tundravm deploy gcp --build build/prover/production/<id> --volume data=create:100GiB
$ tundravm attest prover-1 --policy policies/prover-gcp.json --output attest-1.json
$ tundravm secrets unlock prover-1 data             # OperatorKey(): passphrase over the attested channel
$ tundravm secrets deliver prover-1 --policy policies/prover-gcp.json jwt=@jwt.txt
$ curl --cacert attested-ca.pem https://prover-1:443/status   # through AttestedTLS
$ tundravm deploy upgrade prover-1 --build build/prover/production/<id2>   # section 6.8
```

The policy file is the operator-approved copy of the build's predictions (section 6.5),
and `policies/` is where `new --template prover` puts it.

`Image` keyword slots (all optional, each a list of small typed values):

| Slot | Values | Replaces today |
|---|---|---|

`Image` is a frozen dataclass; slots are tuples after construction; `tundravm.testing`
queries (`plan(image)`) keep working.

### 3.2 `Service`

A small constructor and grouped advanced values, argv only:

```python
Service(
    "taiko",
    [taiko.executable, "--execution-endpoint", nethermind.engine_api],
    requires=[nethermind.ready],
    readiness=HttpProbe("http://127.0.0.1:8080/health"),
    state=data.directory("taiko"),
    credentials=[jwt],
    expose=[TCP(8080)],
    resources=Resources(memory_max="8G", tasks_max=4096),
    shutdown=Shutdown(timeout="120s"),
    hardening=Hardening.preset("dotnet"),
    timer=Every("15m"),                # or socket=Listen(...)
    unit=DropIn(...),                  # anything else systemd knows
)
```

- **argv, never a command line.** A built binary (`GoBinary`, `CargoBinary`, `Build`) is a
  valid first element and pulls its build and install declarations in. `jwt.path` and
  `volume.directory(...)` are typed references rendered through systemd quoting, `$`
  expansion and `%` specifiers correctly; the visible exception for shell is
  `["/bin/sh", "-eu", "-c", script]`.
- **Readiness is real.** `requires=[other.ready]` lowers to `Requires=`/`After=` plus the
  other's readiness mechanism (`Type=notify` with documented `READY=1`, or a bounded
  `HttpProbe`/`TcpProbe`); `After=` alone is never what the user meant.
- **Hardening presets per runtime class.** `Hardening.preset("static")` (today's strict),
  `"dotnet"`, `"jit"`, `"node"`, `"python"`, each tested against a real program of that
  class, with explicit deviations (`Hardening.preset("dotnet", devices=[...])`). The strict
  default stays for static binaries. The renderer, lint and `units convert` are unchanged.
- `working_directory`, `environment`, `user` (defaults to a generated dedicated user),
  `groups` for shared resources, `logs` and `runtime` directories stay typed. Today's 43
  fields are reachable; most of them through the grouped values or `unit=`.

### 3.3 Layer 2: `Component` and `Profile`

A `Component` is today's `@component` class with the same contract (fields are
configuration, `compose()` yields declarations or components, `check()` returns
diagnostics) **plus exports**: typed values a caller can reference without knowing the
component's internals.

```python
execution = Nethermind(jwt=jwt, state=data.directory("execution"))
client = TaikoClient(execution=execution.engine_api, jwt=jwt)
prover = Raiko(l2_rpc=client.rpc, state=data.directory("proofs"))
```

Exports are endpoints with readiness (`execution.engine_api`, `client.rpc`), credential
references, directory bindings with access modes, and the services a caller may depend on
or edit by ref. The resolver keeps today's rules (identity by type plus natural key,
duplicate declarations, cycles, conflicting edits, validation order, `declared_at`
provenance) and gets them written down as a contract. The shipped library
(`tundravm.components`: `Tdxs`, `TeeBase`, `Network`, `Firewall`, `SshAccess`, `DevAccess`,
`Observability`, `Raiko`, `Nethermind`, `TaikoClient`) is made of components.

`Profile` keeps `Variant`'s semantics under mkosi's name:

```python
profiles={
    "staging": Profile(extends="production",
                       changes=[execution.ref.edit(resources=Resources(memory_max="4G"))]),
    "bench": Profile(extends="staging", add=[Benchmarks()], production=False),
}
```

`extends`, typed `changes` against stable refs and `add` stay; a string-keyed `set={}` does
not exist. tundravm resolves the semantics (removing a service removes its unit, preset,
firewall rule and now-unused dependency) and then emits effective mkosi settings and
profile overlays; mkosi profiles select files, they do not do identity-based removal.

### 3.4 CLI: the operator's loop

| Command | Contract |
|---|---|
| `tundravm new NAME [--template service\|prover] [--ci]` | a minimal project with executable examples and optional CI |
| `tundravm check [--profile P] [--tree DIR]` | declarations, references, lint, lock drift, optional committed-tree drift; no image build |
| `tundravm lock [--update [INPUT...]] [--check]` | resolve or check the snapshot, sources, toolchain and firmware-reference pins; stale locks never update implicitly, a missing lock is created on the first `build` |
| `tundravm build [--profile P \| --dev] [--target qemu,azure,gcp] [--reproduce] [--tree-only DIR]` | artifacts, measurements, SBOM, signed manifest into an immutable build directory; refuses a stale lock; `--reproduce` builds again in an independent workspace; `--tree-only` exports the standalone mkosi project |
| `tundravm show [BUILD] [--units\|--tree\|--measurements\|--json]` and `show --diff OLD NEW` | the resolved image or an existing build, with provenance and unchecked guarantees; a diff of packages, files, units, boot payloads, measurements and policy coverage |
| `tundravm run [BUILD] --mode simulated\|tdx [--dev] [--detach]` and `run status\|logs\|stop\|ssh\|mode INSTANCE` | a named local instance with an explicit security mode; `ssh` only where the image permits debug access, with host-key verification through the attested endpoint |
| `tundravm deploy azure\|gcp --build BUILD [--volume NAME=create:SIZE\|existing:ID]` and `deploy status\|logs\|mode\|upgrade\|rollback INSTANCE` | publish and start an explicit build with a deployment receipt; `upgrade`/`rollback` run the one supported replacement workflow (section 6.8) |
| `tundravm attest INSTANCE --policy FILE [--output REPORT]` | fresh evidence verification and coverage report; never delivers anything |
| `tundravm secrets deliver INSTANCE --policy FILE NAME=@FILE...` and `secrets unlock INSTANCE VOLUME` | fresh channel-bound verification, then delivery of credentials, or of the passphrase of an `OperatorKey()` volume; values never touch argv, logs, trees or manifests |
| `tundravm verify BUILD [--require-signature] [--rebuild]` | check the signed artifact set; an independent rebuild only when asked (rebuilding runs the project's code) |
| `tundravm convert PATH --from mkosi\|systemd` | existing trees and unit files into an `Image`, unsupported semantics reported |
| `tundravm doctor [--for build\|run\|tdx\|azure\|gcp]` | one capability at a time, with the exact missing prerequisite |

Twelve commands with subcommands. Gone, folded into the above: `inspect`, `lint`, `compile`,
`diff`, `fetch` (`lock --update` and `build` fetch; `build --offline` uses the lock),
`bake`, `measure`, `sbom`, `evidence`, `changes`, `release`, `witness`, `explore`,
`preview`, `watch`, `status`, `clean` (`build --clean-cache`), `config`, `ci`, `completion`
(generated), `units`, `import`.

### 3.5 Build directories, manifests, instances

```
build/prover/
  production/<build-id>/
    payload.efi          the UKI (the payload that is measured)
    qemu.raw             QEMU: raw GPT disk, ESP + the UKI (never qcow2: section 6.6)
    azure.vhd            when --target azure
    gcp.tar.gz           when --target gcp
    measurements.json    per target and boot path: predictions, unknowns, tool versions
    sbom.spdx.json
    manifest.json        the deterministic build identity (below)
    manifest.sig         optional SSH signature
    inputs/              lock, resolved mkosi summary, source pins, toolchain identity
    tree/                the mkosi project it was built from
    observations.json    timestamps, runner identity, reproduction attempts (not identity)
  development/<build-id>/
  latest-production -> production/<build-id>
.tundravm/instances/<instance-id>/   instance.json, console.log, runtime state
```

A build directory is published atomically after success and never modified. The manifest
binds the artifact bytes, the embedded UKI, the root hash when verity is used, the lockfile,
the tree digest (with file modes and symlink targets), the source inputs, the package
manifest, the SBOM and the toolchain identity; observations (timestamps, runner,
reproduction attempts) stay in their own file. A release is a build identity the deployment record and the verifier policy
refer to, signed. `deploy` never silently picks a development build.

### 3.6 The generated tree: mkosi-native, with the dependency direction right

mkosi builds subimages before the main image and `mkosi vm` boots only the main image, so
the OS is a subimage, the QEMU disk is the main image, and the cloud wrappers are sibling
subimages:

```
tree/
  mkosi.conf                     [Config] MinimumVersion=27.1  Dependencies=payload (+azure,gcp per --target,
                                 passed as --dependency=)   [Output] Format=disk  Output=qemu  Seed=<fixed>
                                 [Content] Bootable=no  ExtraTrees=%O/payload.efi:/efi/EFI/BOOT/BOOTX64.EFI
                                 universal settings: Distribution, Release, Architecture, Snapshot,
                                 ToolsTree*, SourceDateEpoch, OutputDirectory   [Runtime] Firmware=, TPM=, ...
  mkosi.repart/00-esp.conf       [Partition] Type=esp Format=vfat CopyFiles=/efi:/ SizeMinBytes=64M
  payload/                       the OS, included explicitly by the payload subimage
    mkosi.conf                   [Output] Format=uki   [Content] Packages=, KernelModules=, ...
    mkosi.conf.d/10-tee-base.conf, 20-raiko.conf, 30-cloud-glue.conf   one file per concern
    mkosi.profiles/dev/mkosi.conf, mkosi.extra/root/.ssh/authorized_keys   (public keys only)
    mkosi.extra/  mkosi.skeleton/  mkosi.sandbox/  mkosi.build.d/  mkosi.postinst.d/  mkosi.finalize.d/
  mkosi.images/
    payload/mkosi.conf           [Include] Include=../../payload
    azure/mkosi.conf             Dependencies=payload  Format=disk  Bootable=no  (same ESP definition)
    azure/mkosi.postoutput.d/vhd            the retained fixed-VHD converter
    gcp/mkosi.conf, gcp/mkosi.postoutput.d/tar   the retained oldgnu sparse tar.gz
```

With the verity layout the payload subimage is `Format=disk` with root and verity
partitions and `SplitArtifacts=uki`, and the main image and the wrappers copy those
partitions beside the ESP. The tree is regenerated into the build directory on every
build, so no `.mkosi-private/history` ever exists to be replayed, and `Mkosi(settings=)`
refuses `ConfigureScripts=` (lint `mkosi-configure-script`) so that `summary --json`
describes exactly what mkosi builds. Gate 1's evidence is this tree as a committed fixture
with its INI contents and the `summary --json` of every node asserted.

Facts this layout respects (section 4.3 has the citations): subimages do not inherit the
main image's content settings, so the payload includes its directory explicitly; `%O` is a
mkosi specifier and never appears inside repart definitions; `[Match] Profiles=` tests a
selected profile, it does not mean "running on Azure", so every cloud's glue is in the
payload and inert off-platform; profile overlays belong to the configuration directory
that declares them, so `dev` lives under `payload/`, and it embeds public keys only (a
dev artifact is non-production; `run --mode simulated` additionally offers `Ssh=yes` over
vsock with no key in the image). `tundravm build --dev` is `mkosi --profile dev`. Someone
who stops using tundravm keeps a tree that `mkosi build` and `mkosi vm` understand.

### 3.7 Project file, backends, doctor

`[tool.tundravm]` shrinks to `image = "prover.py"` and `build = "build"`. Two backends:
Linux x86-64 (the pinned mkosi imported in-process and run in a forked child, unprivileged
with user namespaces or with `sudo`) and Lima for macOS, which provisions the same pinned mkosi and
tools tree inside an x86-64 Debian guest (today it provisions Nix; both go together). On
Apple Silicon that guest runs under QEMU TCG emulation: identical bytes, several times
slower, documented as such (decision 9.8). Builds never switch backend on failure. `doctor --for` reports independent capabilities:

```
build:x86-64     ready
run:simulated    ready (qemu 9.2, OVMF from the tools tree)
run:tdx          unavailable: no Intel TDX host
deploy:gcp       blocked: no application default credentials
verify:azure     unsupported: Azure evidence is vTPM-bound (section 6.5)
```

## 4. Integrating with the mkosi Python package

The research (`research-2026-10-30/mkosi-lib-report.md`, every claim anchored to `config.py`,
`__init__.py`, `kmod.py`, `qemu.py` of v27.1) settles the question Franco raised:

**There is no library API, but there is a library.** mkosi's CLI is `main()` in
`__main__.py`: signal handlers, `log_setup()`, `resource_path(mkosi.resources)`, then
`parse_config(argv)` and `run_verb(args, tools, images)`. Those two functions are the whole
entry surface, private by convention: v26 → v27 renamed functions, changed the `Config`
JSON shape and moved the privilege model (27's `run_verb` calls `acquire_privileges()` and
`unshare(CLONE_NEWNS)` in the *calling* process, 26 forked first). `Config` has no class
defaults and `Config.default()` reads the host, so configuration is argv plus the file tree
either way. mkosi's own companions (`mkosi-initrd`, `mkosi-addon`) and its test-suite
shell out to `python3 -m mkosi`. Franco's decision (2026-10-30): **import mkosi and run it
in-process, inside mkosi's own `fork_and_wait`**, so the namespace changes stay in a child
while tundravm keeps Python objects, exceptions and the resources path. The file tree stays
the contract that makes leaving tundravm possible.

**mkosi is not on PyPI** (404 on `/simple/mkosi/`), despite the `pyproject.toml`. A pin is
a git tag.

### 4.1 What v2 does

1. **Pin mkosi 27.1 as a dependency and run it in-process.**
   `mkosi @ git+https://github.com/systemd/mkosi@v27.1` in `[project.dependencies]`
   (tundravm itself installs from git, so a direct reference is fine; if tundravm ever goes
   to PyPI the pin moves to `[tool.uv.sources]` or a vendored 1.2 MB zipapp from
   `tools/generate-zipapp.sh`). The emitted `mkosi.conf` carries `MinimumVersion=27.1`; the
   adapter checks `mkosi.__version__` against the pin at import. CI, `doctor` and the README
   lose the "install mkosi" step. Today the README says v26, the host has v26 and CI
   installs whatever `master` is: three versions, none pinned.

   One module, `tundravm/_mkosi.py`, owns every `import mkosi`:

   ```python
   from mkosi.config import parse_config
   from mkosi.run import fork_and_wait
   from mkosi import resources, run_verb

   def invoke(argv: list[str], *, log: Path) -> MkosiResult:
       def child() -> dict[str, object]:
           install_log_handler(log)                  # mkosi logs to the root logger
           with resource_path(resources) as res:     # builtin mkosi-tools, mkosi-initrd configs
               args, tools, images = parse_config(argv, resources=res)
               run_verb(args, tools, images, resources=res)
           return {"images": [c.to_dict() for c in images]}
       try:
           return MkosiResult(fork_and_wait(child))
       except subprocess.CalledProcessError as e:    # die() -> SystemExit in the child
           raise MkosiError(argv, log.read_text()) from e
   ```

   `fork_and_wait` (`run.py:195`) forks, runs the target under mkosi's
   `uncaught_exception_handler(exit=os._exit, fork=True)`, pipes the return value back and
   raises `CalledProcessError` on a non-zero child; `acquire_privileges()` and
   `unshare(CLONE_NEWNS)` therefore happen in the child and tundravm's process stays
   untouched, which is what lets `build`, `run` and the test-suite share one interpreter.
   `die()` is a `SystemExit` in the child, so the parent gets the exit status plus the log
   the child wrote, not a Python exception with a message; the wrapper turns that into
   `MkosiError` with the captured log. Signal handling (`SIGINT`, `SIGTERM`, `SIGHUP`) is
   installed by the wrapper, as `main()` would. `sudo` builds run the same wrapper under
   `sudo -E <venv python> -m tundravm._mkosi` because privilege is per process. Every
   symbol the adapter touches (`parse_config`, `run_verb`, `fork_and_wait`, `resource_path`,
   `Config.to_dict`) is checked against the pinned version by a test that imports them, so a
   mkosi bump fails loudly in CI rather than at a user's first build.
2. **`ToolsTree=default` always, `ToolsTreeSnapshot=` = `Snapshot=`.** The tools tree pins
   `systemd`, `ukify`, `systemd-boot`, `kmod`, `qemu`, `swtpm`, `edk2-ovmf` and `pefile`
   from the same Debian snapshot as the image, which is what the lockfile's `toolchain`
   section gets from nixpkgs today; the tools-tree distribution, release and snapshot are
   pinned explicitly (not inherited from the host) and recorded in the lock beside the
   source commits, package sources, repository keys and EFI-stub inputs the lock already
   keeps. The host needs python3, apt/dpkg with the Debian keyring, and user namespaces
   (or sudo) permitted by its kernel, container and LSM policy; `doctor --for build`
   says which one is missing. The nix backend and the nixpkgs pins go.
3. **`mkosi summary --json` before every build.** The resolved configuration (profiles,
   matches, includes, subimages with scopes applied) is read back without privileges; a
   normalised subset (drop absolute paths and host env; `Seed=` and `SourceDateEpoch=` are
   always set by us) is hashed into `manifest.json` and the lockfile, so "what tundravm
   emitted" and "what mkosi will use" cannot drift silently. Two boundaries: `History=no`
   only stops history from being written, so the tree is regenerated per build and `summary`
   runs with `--force` to make sure nothing is replayed; and `summary` runs before configure
   scripts, so the supported tree has none (`ConfigureScripts=` is refused).
4. **Reproducibility settings set explicitly, not inherited from the host:**
   `SourceDateEpoch=`, `Seed=`, `Snapshot=`, `ToolsTreeSnapshot=`, `ToolsTree=default`,
   `WithNetwork=no` for release builds, `History=no`, `MachineId=` or a shipped
   uninitialised `/etc/machine-id`, no `Environment=` pass-through of host variables.
   (27's `gzip -n` covers mkosi's own compressed outputs; the GCP tarball is built by
   tundravm's converter, which already controls sparse detection, ownership, timestamps and
   gzip headers.)
5. **The same adapter is the only importer of the read-only helpers.** `parse_config` /
   `Config.from_json` resolve a foreign tree in `convert` (replacing most of the 80 KB
   hand-written importer; parsing runs the tree's executable inputs such as `mkosi.version`,
   so `convert` says so and takes `--allow-scripts`); `SETTINGS_LOOKUP_BY_NAME` tells lint
   whether a `Mkosi(settings=)` key exists, in which section and how it parses;
   `kmod.globs_match_*` validate `KernelModules=` globs. `summary --json` is `invoke(["--force",
   "summary", "--json", ...])` through the same path. Nothing calls `build_image` or any
   `Context`-level function directly: the unit of work is a verb, as upstream intends.

### 4.3 mkosi features the tree uses instead of our own

- `mkosi.images/` + `Dependencies=`: the OS is one subimage (`payload`, `Format=uki`, the
  whole root in `.initrd`, including its own configuration directory explicitly because
  subimages do not inherit the main image's content settings); `qemu`, `gcp` and `azure`
  are subimages with `Dependencies=payload`, `Format=disk`, `Bootable=no`, a fixed
  `Seed=`, `ExtraTrees=%O/payload.efi:/efi/EFI/BOOT/BOOTX64.EFI` and a repart definition
  `Type=esp Format=vfat CopyFiles=/efi:/` (repart paths are image-root relative; `%O` is
  expanded by mkosi, never inside repart files); the main image is `Format=none` with
  `Dependencies=` naming the targets asked for. Azure's fixed VHD
  (`qemu-img convert -O vpc -o subformat=fixed,force_size` plus the footer normalisation
  we have) and GCP's `disk.raw` in an oldgnu gzip archive are **not** mkosi output formats:
  tundravm's converters stay, generated into `mkosi.postoutput.d/`. Gate 1 starts with a
  spike of exactly this layout; the fallback is today's `systemd-repart` post-output
  script under the same `mkosi.images/` shape.
- `mkosi.profiles/dev/` under the payload's configuration directory (profile overlays
  belong to the directory that declares them): console, sshd, root login,
  `[Output] ImageId=%i-dev`.
- `mkosi.conf.d/*.conf` with `[Match] Image=`, `[Match] Profiles=`: per-component settings,
  one file each, readable by name. Not cloud dispatch: `[Match] Profiles=azure` selects a
  profile, it does not mean "running on Azure"; the cloud glue is in every payload, gated
  at boot by `ConditionVirtualization=`.
- `mkosi.sandbox/`: apt sources (backports, extra repositories) that never enter the image.
- `mkosi.credentials/`, `Ssh=yes`: dev-profile SSH over vsock (`mkosi ssh`) with no port
  forwarding and no key in the image.
- `mkosi.repart/` + `Verity=`: the verity-root layout (5.2 item 6).
- `mkosi.uki-profiles/`: only if one UKI ever needs two cmdlines.
- `systemd-sysusers`, `systemd-tmpfiles`, `systemctl preset-all`, `systemd-firstboot`: units
  and users are files under `mkosi.extra/` and presets; no `systemctl enable` in postinst.

follows is the deeper layer: their runtime chain end to end, measured against what tundravm
ships today, and the items that belong in v2. The full report (`research-2026-10-30/flashbots-report.md`,
section 3.8 and 6) has the citations.

### 5.2 What v2 takes from it

Ordered by value to "a TDX image of my service in twenty lines"; sizes S/M/L.

1. **Prove which Debian drivers survive a built kernel, then enforce it (M, correctness).**
   The flashbots study claimed `olddefconfig` turns every `=m` into `n` under
   `CONFIG_MODULES=n`; the kernel's `symbol.c` promotes `m` to `y` instead, so the truth is
   per option (dependencies on module-only symbols can still drop a driver). Gate 1 records
   a before/after config of `Kernel.build(...)`. Independently of the outcome:
   `CloudDrivers(targets)` is a `KernelConfig` derived from the same tables
   `kernel_modules.py` already has (`TDX_GUEST_MODULES`, `AZURE_MODULES`, `GCP_MODULES`,
   `DISK_MODULES`, `FIREWALL_MODULES`) that the post-`olddefconfig` check asserts as `=y`;
   an encrypted `Volume` contributes `CRYPTO_USER_API_*=y`; `run --probe` checks
   `/sys/class/net/*` and `/dev/tdx_guest` after boot; `BLK_DEV_PCIESSD_MTIP32XX` joins the
   hardening deny list. `mod2yesconfig` is used only if the before/after config shows it is
   needed.
2. **Verified first contact (M, trust).** Every image runs the attested endpoint of
   section 6.3, which serves its SSH host keys inside the quote-bound transcript,
   independent of the data disk. `tundravm attest INSTANCE --policy FILE` writes
   `known_hosts` only when the quote verifies against the operator-approved policy. Root-
   owned key directory, read-only to everything else, with a negative boot test.
3. **Egress in the firewall (L, security).** `Network(egress=Egress(always=[...],
   modes={"maintenance": ..., "production": ...}, initial="maintenance"))` renders one
   nftables ruleset with default-DROP output; `run mode production` / `deploy mode production`
   (a oneshot in the image) switches chains and flushes conntrack. Lint `egress-unfiltered` warns on a release build
   without it. `Service(egress=[...])` comes later.
4. **Two disk-unlock models (M).** `Volume(unlock=TpmSeal(...))` (today's sealed random key,
   with its platform trust boundary stated) and `Volume(unlock=OperatorKey())`: LUKS2
   passphrase supplied over the attested channel each boot, the delivered SSH public key
   kept in a LUKS2 token. `tundravm unlock INSTANCE` sends it (section 6.2). Lint
   `volume-tpm-on-cloud` (info) points at the alternative.
5. **Runtime measurement visibility (S).** The attestation service prints `RTMR0..3` to the
   console at boot and exports the CCEL RTMR1 authenticode hash as a textfile metric, so a
   fleet can match images without a quote round-trip; `build` prints the same hash.
6. **Verity root for large images (M).** `rootfs=RootFS.verity(filesystem="erofs")` (section
   6.6): `Format=disk`,
   `SplitArtifacts=uki`, erofs root with `Verity=data`, `systemd.volatile=overlay`, kernel
   options `DM_VERITY EROFS_FS* OVERLAY_FS CRYPTO_SHA256`, the cloud wrappers reusing the
   `.raw`. Default stays the UKI-with-rootfs for images under a few hundred MB.
7. **Boot probes derived from declarations (M).** `run --probe` (and the CI boot job) asserts
   hardened kernel
   symbols absent from `/proc/kallsyms`, egress denies from inside the guest, host-key
   directory immutable, `systemd-analyze security` under a ceiling, printed RTMRs equal to
   `measurements.json` under TDX. Nobody keeps a checklist by hand.
8. **Small (S each).** GCP glue with Google's `google_nvme_id` and udev rules, hostname from
   metadata, forwarded-IP routes; root tmpfs cap (`RootFS.initramfs(max_size="4G")`); the
   fail-safe
   idiom (a setup task writes nothing on failure, the consumer has `ConditionPathExists=`);
   lint `snapshot-missing` on release builds; a build report table (part, version, cached,
   size, duration); re-verify Azure VHD reproducibility; while the legacy SSH-key delivery
   on :8080 still exists, state its one-shot semantics (one key, once, then the port closes);
   the section 6.3 endpoint replaces it and is not one-shot.

Deferred to shipped components, after v2 core: `Container()` tenant sandbox with netns denies
derived from the host egress rules and digest-pinned images; `Observability(remote_write=)`
through a fixed-IP proxy; `BootTemplate` (schema-bound values rendered at boot) with lint
`unit-written-at-runtime` (flashbots' L2 renders `op-rbuilder.service` from Vault at boot, so
the attested image does not pin what the builder runs: the thing to refuse, not copy).

### 5.3 The v2 attestation and secrets story

flashbots' chain, trimmed to the pieces that matter, becomes the default of every image
(the protocol itself is section 6.3):

```
boot ──► network, time
     ──► evidence service (tdxs) on /run/tdx/quote.sock, as user tdxs
     ──► attested endpoint on :8745: a key pair made in the guest; the quote binds
         sha512(purpose ‖ nonce ‖ public key ‖ SSH host keys); TLS with that key
     ──► tundravm attest INSTANCE --policy FILE      verdict + coverage, known_hosts on success
     ──► tundravm secrets deliver INSTANCE ...       fresh verification, then credentials
     ──► tundravm secrets unlock INSTANCE VOLUME     OperatorKey() volumes
     ──► application services (requires=[evidence.ready, jwt.ready, data.ready])
```

The endpoint depends on nothing on the volume (today's prover wires
`Tdxs(needs=[secrets.ready])`, which would deadlock this chain). The in-image half lives
in tundra-tools (Go): the quote service exists; the endpoint, the credential drop and the
LUKS-token passphrase path are new work (gate 3). Until then `attest` keeps the relay over
SSH, marked `unverified first contact` in its output.

### 5.4 Smells not to copy

Units rendered from secrets at boot; three hand-kept copies of every network fact (host
rules, container denies, `/etc/hosts`); `ubuntu:24.04` pulled by tag and `apt-get` at every
container start; `rustup` at build time and tag-based clones; everything root; a patched
unreleased mkosi commit; hand-bumped snapshots with one image on no snapshot at all; a
hand-maintained regression checklist. Each of these is something v2's lint or lockfile
refuses by construction.

## 6. Runtime contracts to specify before the API freezes

The first draft hid these behind `Disk("/persistent", encrypted=True)`, `Secret("jwt")` and
"one measurement set". The review was right that each conceals a decision a user meets at
their first upgrade. Each contract below is a short design note (one page) written and
reviewed before the phase that implements it.

### 6.1 Execution modes

`run --mode simulated` and `run --mode tdx`; `deploy` is always TDX. A production profile
refuses to start its services without a TDX quote path: `tdx-evidence.service` positively
checks for TDX (`/dev/tdx_guest` or configfs-tsm, a test quote) and fails otherwise, and
every application service has `Requires=`/`After=` on it (`ConditionSecurity=` knows only
`cvm`, not `tdx`, and a failed condition does not propagate through `Requires=`, so a
condition is not enough). The dev profile may run simulated and its evidence carries
`simulated: true`. Verifiers reject simulated and debug-enabled evidence for production
policies. No fallback, ever.

### 6.2 Volumes

A `Volume` is a logical disk with a stable identity mapped to a QEMU serial or a cloud
attachment (`deploy --volume data=create:100GiB|existing:ID`); capacity is deployment
configuration. Creation, attachment, initialisation and unlock are separate steps;
formatting happens only on a positively identified, empty, authorised volume; an unlock
failure is never permission to reformat. Unlock policies: `OperatorKey()` (LUKS2 passphrase
over the attested channel each boot, the SSH public key kept in a LUKS2 token so the control
plane works before the disk opens), `TpmSeal(platform=, pcrs=, recovery=)` (a random key
sealed to a vTPM, with the trust boundary stated per platform: Azure's paravisor-backed
vTPM, GCP's software-attested vTPM, local swtpm with persisted state, none of them
interchangeable), `BrokerKey(url, audience)` (released by a key broker after attestation,
for unattended fleets). Ownership for several services sharing a volume goes through
`volume.directory(name, group=)`. Backup, resize and rollback protection are documented as
not provided.

### 6.3 Attested endpoint and secret delivery

Bootstrap order: network and time → evidence service → attested endpoint (:8745), which
is the control plane and is *ready* on its own → secret delivery and volume unlock →
application readiness. The endpoint depends on nothing on the volume; control-plane
readiness and application readiness are two different states that `run status` and
`deploy status` report separately.
Protocol: the guest generates a key pair at boot, the quote's `report_data` binds
`sha512(purpose ‖ nonce ‖ public key ‖ SSH host keys)`, and the client speaks TLS to a
certificate carrying that key, so a relayed quote cannot authenticate a different
connection. The verifier checks the quote chain, collateral and TCB policy, debug
attributes, and full measurement coverage against an operator-approved policy; verdicts
keep today's `trusted` / `partial` / `measurements-match` / `simulated`. The release
predicate is executable and tested with its rejections: production delivery requires
`trusted`, a fresh channel binding to the recipient key, an approved production build
identity and no debug attributes; partial coverage, simulation, a replayed quote and a
wrong recipient key are each a named test. It never reuses today's `Attestation.passed`,
which accepts weaker verdicts on purpose. `secrets deliver` performs its own fresh
verification and writes each value atomically to `/run/tundravm/credentials/<name>`
(root-owned tmpfs, mode 0600); a service binds it with `LoadCredential=<name>:<path>`, so
systemd copies it into the unit's read-only credential directory at start. That copy is
why rotation is `restart` (re-delivery restarts the bound units) or `none`; a `reload`
rotation would need a directory binding instead of a credential and is not offered until
it exists. Startup timeouts, required versus optional secrets and behaviour during broker
outages are stated. A broker (`BrokerKey`, `Secret(source=broker.secret(...))`) is the
same protocol with a pull client; the CLI is the bootstrap and debugging path. The in-image
half is tundra-tools (Go) work: the quote service exists; the endpoint, the credential drop
and the LUKS-token passphrase path are new.

### 6.4 Ingress and observability

`expose=[TCP(8080)]` opens the firewall; it does not protect requests. `AttestedTLS(port,
upstream=)` is the confidential ingress: the certificate is bound to the quote, the client
verifier policy, backend bind address, client authorisation and renewal are part of the
contract, and whether a cloud load balancer passes TLS through is a deployment fact
recorded in the receipt. `TLS(port, certificate=)` is ordinary HTTPS with a different name.
`Observability(logs=JournalExport(url, credential=), metrics=PrometheusRemoteWrite(url,
credential=))` is the authenticated export path for a VM with no console and a volatile
journal: bounded buffers, retries, through a fixed-IP proxy with SNI when egress is
restricted, and never blocking application start (`ConditionPathExists=` on the rendered
config).

### 6.5 Measurements: records, not "one set"

One UKI gives one payload, not identical registers across boot paths and platforms.
`measurements.json` holds per-target, per-boot-path records: the measurement tool and
version, stub and kernel identity, digest algorithm, boot mode (direct UKI, raw disk with a
GPT event), artifact-to-payload binding, expected values, explicit unknowns (platform
registers a QEMU or portable policy leaves to the verifier), RTMR3 recorded as outside the
policy unless an event schema is defined, and firmware pairing preserved (an MRTD and an
RTMR0 from different firmware candidates never match together). Azure keeps its vTPM-bound
scheme and stays refused by the TDX-only `attest`. Predictions (build), observations
(`attest --output`) and the operator-approved policy are three files, never one.

### 6.6 Root-filesystem layouts

Two, chosen explicitly and recorded in the manifest, never switched by a size threshold:
`RootFS.initramfs()` (the OS in the UKI's `.initrd`; small services) and
`RootFS.verity(filesystem="erofs")` (`Format=disk`, root data and verity hash partitions,
root hash on the UKI command line from repart, `systemd.volatile=overlay`, the initrd
carrying dm-verity and erofs, the cloud wrappers carrying the root and verity partitions
too). The QEMU artifact is a raw GPT disk because today's `_gpt_event()` reads raw GPT;
qcow2 would be a measurement regression. Today's replay tests are offline vectors and the
template boot tests launch the UKI directly with `-kernel`, so measuring the raw-disk boot
path against a real quote is gate-2 work, not existing coverage.

### 6.7 Kernel

`Kernel.default()` is one tested kernel with a published matrix: version and provenance,
TDX report and quote interfaces, ACPI behaviour per platform, virtio, Hyper-V, NVMe, gVNIC,
TPM, dm-crypt, dm-verity, erofs in the initrd, module policy, and compatibility with .NET
JITs, Rust provers and the exporters. `Kernel.build(...)` keeps Debian's `=m` drivers (the
`mod2yesconfig` fix from section 5.2) and records source, config, patches, compiler and
binary identity in the manifest. flashbots' cmdline (`nospectre_v2`) is a deliberate
choice to make, not a default to copy.

### 6.8 One upgrade path

Replacement VMs with persistent-volume reattachment: build → approve the policy at the
verifier → launch the candidate → attest, deliver credentials, control plane ready → drain
the old instance → fence it and transfer exclusive volume ownership (expected downtime
stated) → unlock on the candidate → application readiness → retire the old policy when the
rollback window closes. A stateful service cannot be application-ready before it owns its
volume, so readiness comes after the transfer, not before. `deploy upgrade|rollback` run
it and refuse incompatible volume or schema transitions; schema migrations stay explicit.
No in-place package upgrades, no A/B slots.

## 9. Decisions for Franco

1. **Drop the byte-identical nethermind-v1 golden tree?** It pins the compiler to a 2024
   layout and costs ~6 000 lines. Proposal: keep `examples/surge-tdx-prover` as an `Image`
   over `tundravm.components` whose converted stack boots, measures and recovers state in
   CI; drop byte parity. Section 3.6 depends on it.
2. **Rename `Recipe` → `Image`, `Variant` → `Profile`, keep `Component`, drop `Fragment` and
   `Composite`?** Cheap now, aligned with mkosi, breaks every example once, no aliases.
3. **Audit stack.** Fold evidence, release and witness into the signed manifest, `build
   --reproduce` and `verify`, or keep the bundle schemas as a separate package? Proposal:
   fold; nobody consumes the schemas yet.
4. **Secret delivery model.** Operator push (`secrets deliver`) first with the broker as
   the same protocol later, or a broker from the start? Proposal: push first; it is the
   flashbots-proven path and needs no new service.
5. **A TDX host for gate 2.** Nothing in sections 6.1, 6.3 or 6.5 can be called done on
   this machine; the quote path, configfs access and the measurement records need
   hardware. Which host, and GCP credentials for the first cloud proof?
6. **Default QEMU artifact: raw disk** (measured GPT boot path, same as the clouds) instead
   of the direct-UKI boot today. Agreed?
7. **Backends.** Linux and Lima only; drop nix and inprocess once the tools tree carries
   the toolchain pin.
8. **Apple Silicon.** The faithful option is an x86-64 Lima guest under TCG emulation
   (slow); the fast options (an aarch64 guest cross-building, or Rosetta) change the bytes
   or were already rejected for determinism. Which one, or a remote Linux builder instead?

## 10. Risks

- **mkosi has no API promise.** The in-process adapter touches five private symbols
  behind one version guard and an import test; a mkosi bump is a deliberate change with a
  re-audit of `run_verb`'s privilege dance, never a floating dependency. The file tree stays
  the contract.
- **`mkosi vm` and TDX.** No TDX code upstream; v2 keeps its own TDX runner and tries the
  `Firmware=linux` + `QemuArgs=` path (or an upstream `Firmware=tdx` patch) on a TDX host.
- **The wrapper layout is a spike.** If a `disk` subimage with `Bootable=no` cannot take
  the payload's UKI by `ExtraTrees=` and `CopyFiles=`, the post-output `systemd-repart`
  wrapper stays, under `mkosi.images/` all the same. VHD and GCP packaging keep tundravm's
  converters in any case.
- **Gate 3 is the long pole and is Go work** in tundra-tools, with a protocol that has to
  be reviewed for the relay attack before it ships.
- **Gate 1 is not two days.** Tools-tree bootstrap, Lima re-provisioning and the host
  capability matrix are each a day of surprises.
- **Scope.** Six gates are roughly eight weeks of focused work; agents may implement gates
  4 and 5 in parallel once gate 3's notes are reviewed, and nothing is accepted out of
  order (section 8).
