Headline facts, each expanded below:

1. There is no public Python API. `parse_config()` + `run_verb()` are the only "entry points" and both are private by convention; mkosi's own companion tools (`mkosi-initrd`, `mkosi-addon`) and its test-suite **shell out** to `mkosi`/`python3 -m mkosi` rather than call these functions.
2. `run_verb()` in 27 unshares the **calling process's** user and mount namespaces (`MK/mkosi/__init__.py:5134-5171`). In 26 that happened inside a forked child (`HOST26/__init__.py:4855-4868`, `fork_and_wait(run_build, ...)` at 5047/5225). Calling `run_verb` in-process from tundravm would namespace the tundravm process itself.
3. `Config` is a frozen dataclass with a tested JSON round trip (`to_dict`/`from_json`, `tests/test_json.py`); `mkosi summary --json` dumps it; configure scripts receive and return it. That is the closest thing to a stable interface, and it changed shape between 26 and 27 (`Credentials` dict -> list of objects, `UnitProperties` removed, `DebugTiming`, `OutputSize`, `OciLabels`, `ElTorito*`, `SignInitrdPCRs`, `MakeScriptsExecutable`, `ForeignUIDRange`, `UMask`, `DelegateRanges`, `DiskType`, `ToolsTreeSnapshot` added).
4. mkosi is **not on PyPI** (`https://pypi.org/pypi/mkosi/json` -> 404, `/simple/mkosi/` -> 404). Pinning means a git URL dependency or a vendored zipapp.
5. mkosi 27 has **no TDX/SEV support** in `qemu.py` (grep for `tdx`, `sev`, `confidential`, `kernel-hashes`, `memory-encryption` across `mkosi/` returns nothing) and **no measurement/prediction code** of its own: PCR 11 pre-computation is delegated to `ukify`/`systemd-measure` (`--pcr-banks sha256`, `--policy-digest`), RTMR/MRTD do not appear anywhere.
6. tundravm does **not** reimplement the kernel-module closure in Python. `TV/kernel_modules.py` is curated module sets; the closure is mkosi's `KernelModules=`; tundravm adds a bash finalize check (`TV/compiler/emit_mkosi.py:1864-1925`) that covers two real gaps in `MK/mkosi/kmod.py`: softdeps that name an alias are dropped (`kmod.py:316-317`), and `depmod` is not re-run after pruning (`__init__.py:3105-3123`).

## 1. Library entry points

### 1.1 argv to build

`MK/mkosi/__main__.py:31-49`:

```python
@uncaught_exception_handler()
def main() -> None:
    signal.signal(signal.SIGINT, onsignal) ...
    log_setup()
    with resource_path(mkosi.resources) as resources, stash_terminal_title():
        args, tools, images = parse_config(sys.argv[1:], resources=resources)
        ...
        run_verb(args, tools, images, resources=resources)
```

`parse_config` (`MK/mkosi/config.py:5531-5774`):

```python
def parse_config(argv: Sequence[str] = (), *, resources: Path = Path("/"))
    -> tuple[Args, Optional[Config], tuple[Config, ...]]:
```

Flow: argparse into `ParseContext.cli` (5540-5547) -> `Args.from_namespace` (5549) -> early return for verbs that need no config (5577-5578) -> `finalize_configdir(args.directory)` (5580; honours a `mkosi/` subdirectory, `config.py:5446`) -> history replay from `.mkosi-private/history/latest.json` if `have_history()` (5588-5612) -> `parse_new_includes()` for CLI `--include` (5622) -> `parse_config_one(configdir, parse_profiles=True, parse_local=True)` (5633-5635) -> `context.finalize()` (5637) -> write history (5641-5650) -> default tools tree via `finalize_default_tools` (5652-5659) -> `mkosi.images/` subimages, each a fresh `context.config` with inherited settings (5686-5737) -> `Config.from_dict` (5742-5743) -> default initrd subimage via `finalize_default_initrd` (5745-5770) -> `resolve_deps` (5772) -> returns `(args, tools, (subimages..., main))`. The main image is always last.

`run_verb` (`MK/mkosi/__init__.py:5056-5449`): verb dispatch for `init`, `completion`, `documentation`, `genkey`, `dependencies` (5088-5096, itself re-entering `parse_config(["--directory=", "--repositories=", *args.cmdline, "--include=mkosi-tools", "build"])`), `summary` (5104-5118, `--json` dumps `{"Tools": tools.to_dict(), "Images": [c.to_dict() ...]}`), `cat-config`, `bump`, `latest-snapshot`; then **in-process** `acquire_privileges(...)` (5142-5165) and `unshare(CLONE_NEWNS)` (5170); `clean`; default tools tree build (5183-5223); `run_configure_scripts` per image (5322); dependency re-resolution (5327); the build loop `build_image(Context(args, config, workspace=..., resources=..., keyring_dir=..., metadata_dir=..., package_dir=...))` (5377-5412, call at 5403); finally `shell/boot/vm/qemu/serve/burn/sysupdate` dispatch (5432-5449).

`build_image` (`MK/mkosi/__init__.py:4080-4282`) is the whole pipeline in one function: sandbox trees, base trees, cache reuse, `distribution.installer.setup/install`, prepare scripts, `run_depmod(cache=True)`, `save_cache`, build scripts, extra trees, postinst, `install_systemd_boot/grub/shim`, `run_sysusers/tmpfiles/preset/depmod/firstboot/hwdb`, remove packages/files, finalize scripts, `normalize_mtime`, `make_disk`, `install_kernel` (UKI), output-format switch (`make_uki`, `make_esp`, `make_tar`, `make_cpio`, OCI, directory), compression, checksum, signature, manifest, postoutput scripts.

### 1.3 Stability, import side effects, privileges

- Nothing is documented as a Python API. `docs/` and `README.md` mention Python only as an install method (pipx/venv/zipapp, README 49-87). `pyproject.toml` ships `mkosi`, `mkosi.distribution`, `mkosi.installer`, `mkosi.resources` with `package-data` for `man/*`, `mkosi-initrd/**`, `mkosi-tools/**`, `mkosi-vm/**`, `repart/**`, `tmpfiles.d/*`; console scripts `mkosi`, `mkosi-initrd`, `mkosi-sandbox`, `mkosi-addon`. Public-looking helpers exist (`Config`, `Args`, `parse_config`, `Verb`, `Distribution`, `dump_json`, `kmod.*`, `run`, `rmtree`, `copy_tree`), and `tests/` imports them, but between 26 and 27 functions were renamed/removed without notice: `__init__.py` lost `run_build`, `want_initrd`, `remove_cache_entries`; gained `check_script`, `repository_metadata_needs_sync`, `run_locale_gen`; `qemu.py` lost `machine`, `scope_cmd` and moved `vsock_notify_handler`; `config.py` gained `Credential`, `QemuDiskType`, `config_default_initrds`, `config_make_credential_parser`, `config_parse_int`, `finalize_historydir`, `want_prebuilt_uki`. Treat every symbol as private.
- Import side effects: none worth worrying about. Module-level code is constants, `ContextVar`s (`log.py:22-27`), compiled regexes (`__init__.py:172`), `ctypes` struct definitions (`sandbox.py:125-160`). `log_setup()` (`log.py:158`) installs a root-logger handler only when `main()` calls it. `die()` is `logging.error(...)` + `sys.exit(1)` (`log.py:40-44`), so any library call can raise `SystemExit`. `uncaught_exception_handler` (`run.py:88-147`) converts exceptions to exit codes and is only applied in `main()` and in `fork_and_wait` children.
- Privileges: `run_verb` calls `acquire_privileges(foreign=..., delegate_ranges=...)` (`__init__.py:5142-5165`, falling back to a plain `unshare(CLONE_NEWUSER)` via `unprivileged_userns` `sandbox.py:789-853`, which forks a helper to write `uid_map`/`gid_map` of the **current pid**), then `unshare(CLONE_NEWNS)` (5170). From then on the process is root inside a user namespace with a private mount namespace. mkosi 26 did this inside `fork_and_wait(run_build, ...)` (`HOST26/__init__.py:4855-4868, 5047, 5225`), so a 26 caller's process stayed intact; 27 moved it up. Every sandboxed subprocess is then run through `mkosi-sandbox` (`run.py:645-811` builds argv for `sandbox.py:1440 enter()`), which needs unrestricted user namespaces (Ubuntu AppArmor sysctls, `mkosi.1.md:3458-3480`), `mount_setattr()` (kernel >= 5.12, `mkosi.1.md:3445`) and systemd >= 254 on the tools side for bootable disks (3446).
- Companion tools confirm the intended boundary: `mkosi-initrd` builds an argv and runs `run(["mkosi", "--force", "--directory=", ... "--include=mkosi-initrd", ...])` (`MK/mkosi/initrd.py:340-440`), `mkosi-addon` likewise (`addon.py:46-80`), and the test-suite `Image.mkosi()` runs `["python3", "-m", "mkosi", "--debug", *options, verb, *args]` (`MK/tests/__init__.py:56-77`). The only in-process use of `parse_config` outside `main()` is for config computation: `conftest.py:44-47` (`parse_config(["-d", str(distribution)], resources=resources)[2][0]` to read the local snapshot), `tests/test_config.py` (`with chdir(d): _, _, [config] = parse_config([...])`, 95-130 and 239-252), the `dependencies` verb (5088-5096), and `finalize_kernel_modules_include` re-parsing the builtin initrd config (`__init__.py:1546-1552`).

## 2. In-memory configuration

### 2.1 Feeding settings without a config tree

Every setting in `SETTINGS` has a long option (`ConfigSetting.__post_init__`, `config.py:1848-1851`: `--{dest with dashes}`), so a complete configuration can be passed on the CLI. The two mechanisms that matter:

- `--directory=''` (empty) makes `finalize_configdir` return `None` so **no** config is read from the cwd (`mkosi.1.md:275-281`, `config.py:5446-5458`); `mkosi-initrd` relies on this (`initrd.py:342`).
- `--include=PATH` / `-I` (`config.py:2772-2781`, docs `mkosi.1.md:2336-2353`): a file or a directory. Directories are parsed through `parse_config_one(path, parse_profiles=path.is_dir())` (`config.py:4997-4998`), which means an included directory contributes `mkosi.conf`, all `path_suffixes` files (`mkosi.extra`, `mkosi.build`, ...), `mkosi.conf.d/`, and `mkosi.profiles/` (5184-5300), but **not** `mkosi.local.conf` (`parse_local` defaults False, 5179-5192), **not** `mkosi.images/` (only `configdir / "mkosi.images"` is scanned, 5686-5688), **not** `mkosi.tools.conf`/`mkosi.initrd.conf` (`configdir` only, 5387-5389 and 5438-5440), and no history. Includes dedupe by inode (4971-4976). Builtin names `mkosi-initrd`, `mkosi-tools`, `mkosi-vm`, `mkosi-addon`, `mkosi-obs` resolve to `mkosi/resources/<name>` (`config.py:68`, 4964-4968).
- CLI includes are parsed **after** all CLI arguments (4960, docs 2338-2341); file includes immediately.
- There is no `-S`/`--settings key=value` generic option and no environment-variable form of settings. Environment only feeds `MKOSI_HOST_DISTRIBUTION/RELEASE` (defaults, 1048-1070), `SOURCE_DATE_EPOCH` (1116), proxies (1128-1143), `MKOSI_DNF`, `MKOSI_IN_BOX`, `MKOSI_DEFAULT_TOOLS_TREE_PATH` (box internals), `MKOSI_FORCE_USERNS_FALLBACK` (27.1), `MKOSI_LESS`, `GNUPGHOME`, `TERM`.
- `[Include]`-section `Include=` in a conf file is the same mechanism (`parse_new_includes` is called after each setting, 5271).

Precedence (`finalize_value`, `config.py:5000-5071`): CLI wins; for lists/dicts/sets the CLI value is **appended/merged** onto the config-file value unless the CLI assigned the empty string (`_was_none` marker); `mkosi.local.conf` values are promoted into the CLI namespace (5185-5192). Delayed specifiers `&d &r &a &i &v &I` exist only for `CacheKey=`, `BuildKey=`, `Linux=` (2555-2576).

### 2.3 `Config.to_dict()` as a build fingerprint

What it is good for: it is the fully resolved configuration **after** defaults, includes, profiles, `[Match]`, specifiers and history, and it is byte-stable for a given mkosi version (`tests/test_json.py` compares literal dumps). `mkosi summary --json` prints it without building (`run_verb` 5104-5116) and without needing privileges (it returns before `acquire_privileges`).

Why it is not a reproducible fingerprint as-is:

- `Files` (`Config.files`, 2107) lists absolute paths of every parsed config file.
- `Seed` defaults to a **random UUID** per parse when `Seed=`/`mkosi.seed` is unset (docs `mkosi.1.md:801-808`; `make_image` passes `--seed` to repart at `__init__.py:3496`). Two `summary --json` runs differ unless the seed is pinned.
- `OutputDirectory`, `WorkspaceDirectory`, `CacheDirectory`, `PackageCacheDirectory`, `BuildDirectory`, `ToolsTree` (resolved to the tools tree output path, 5658), script and tree paths are absolute host paths.
- `Environment` includes pass-through variables; `SourceDateEpoch` is defaulted from the host env (1111-1117); `Distribution`/`Release`/`Architecture` default from the host (1047-1081); `RepositoryKeyFetch` depends on the host/tools distribution (1095-1108).
- It is captured **before** `ConfigureScripts=` run (`mkosi.1.md:2596-2602`), so it is not what the build used if configure scripts rewrite settings.
- `image_version` may come from executing `mkosi.version`.

A normalised subset (drop `Files`, `*Directory`, `ToolsTree`, `Environment` pass-throughs, require `Seed`/`SourceDateEpoch`/`Snapshot` to be set) would be a usable fingerprint; mkosi's own cache key is a much smaller hand-picked dict, `Config.cache_manifest()` (`config.py:2518-2553`: distribution, release, mirror, local_mirror, snapshot, architecture, package manager, packages, build_packages, package directory file names + mtimes, repositories, overlay, base64 of prepare scripts), compared in `have_cache()` (`__init__.py:3368-3409`). Note that it ignores extra/skeleton trees, scripts other than prepare, and everything after the cache point by design.

## 3. Subsystems tundravm has that mkosi also has

### 3.1 `mkosi/kmod.py` (kernel modules and firmware)

What tundravm actually does today (correcting the task's premise): `TV/kernel_modules.py` holds curated module sets (`TDX_GUEST_MODULES`, `AZURE_MODULES`, `GCP_MODULES`, disk/firewall sets) and `module_selection()` (173-193); `TV/compiler/emit_mkosi.py:1688` writes them as `KernelModules=`; the closure itself is mkosi's. tundravm adds a finalize-script check (`emit_mkosi.py:1864-1925`) that (a) asserts each listed module is a `.ko` or builtin, (b) walks `modules.dep` lines of listed modules and fails on a dep missing from the image, (c) resolves `pre:` softdeps through `modules.alias`, (d) re-runs `depmod -a` with `mkosi-chroot`. `CHANGELOG.md:225` records why: `libcrc32c`'s alias softdep `crc32c` is not followed by mkosi and mkosi "skips depmod when only `KernelModules=` is set, leaving a stale index".

mkosi 27 semantics, from the code:

- Entry: `run_depmod(context, cache=False)` (`__init__.py:3077-3123`) called twice from `build_image`: with `cache=True` right after package install/prepare (4118) and plain after `run_preset` (4159). The non-cache call prunes via `process_kernel_modules()` (`kmod.py:452-508`) for every valid `/usr/lib/modules/<kver>` (`is_valid_kdir`, 511-519), with include list `finalize_kernel_modules_include()` (`__init__.py:1538-1562`: expands `default` by re-parsing `resources/mkosi-initrd`, `host` via `/proc/modules`).
- Filtering (`filter_kernel_modules`, `kmod.py:77-134`): `KernelModules=` globs (new syntax, plain list parser `config.py:3471-3478`) with `-` negation, last match wins (`globs_match_filename`, 34-59: basename, path-suffix, absolute-under-`kernel/` and absolute-under-`<kver>/`, directory with trailing `/`, `_`/`-` normalised 186-201); deprecated `KernelModulesInclude=`/`KernelModulesExclude=` regexes are stored as `re:` prefixed strings (`parse_kernel_module_filter_regexp`, 2744-2747) in `kernel_modules_include`/`kernel_modules_exclude`. If only includes are set, **only** the matched modules are kept (128-130) before dependency resolution. Devicetree globs: `filter_devicetrees` (522-559).

In the final pass, after pruning, depmod is skipped when the deprecated `kernel_modules_exclude` is empty and `modules.dep` is newer than every remaining `.ko` (3105-3113), which is exactly the post-prune state (the pruned files are gone, the survivors are older than the index). - Library usability: `globs_match_*`, `normalize_module_*`, `module_path_to_name`, `all_modules`, `filter_kernel_modules(root, kver, include=, exclude=)`, `filter_firmware(root, ...)` and `filter_devicetrees` are pure functions over a root path (tested in `tests/test_kmod.py` without any sandbox). `modinfo`/`resolve_module_dependencies`/`required_kernel_modules`/`process_kernel_modules` take a `Context` (needs `config`, `root`, `sandbox`) and run `modinfo` through `mkosi-sandbox`/`chroot_cmd` (`run.py:844`), i.e. they need the namespace set-up. ## 6. Debian specifics (`MK/mkosi/distribution/debian.py`, `installer/apt.py`)

- Repositories (`debian.py:42-118`): `main` + `Repositories=` as **components** (contrib, non-free, non-free-firmware); `Mirror=` or `https://snapshot.debian.org` when `Snapshot=` is set, else `http://deb.debian.org`; with a snapshot the URL becomes `<mirror>/archive/debian/<snapshot>` (66), debug `archive/debian-debug/<snapshot>` (82), security `archive/debian-security/<snapshot>` (108); without snapshot, `-updates` (98-104) and `-security` on `deb.debian.org/debian-security` (27.1 change); no `-updates` suite when snapshotting; nothing for `sid`/`unstable` beyond main+debug (94-95). A custom `Mirror=` together with `Snapshot=` must therefore have the snapshot.debian.org layout. `LocalMirror=` (48-56): single plain `deb <url> <release> main` with `Trusted: yes` (`AptRepository.__str__`, `apt.py:27-37`), for fully offline builds. `for_image=True` strips mirror and snapshot so the image's own `/etc/apt/sources.list.d/<release>.sources` points at `deb.debian.org` (45-46, 234, 271-278).
- The deb822 `Snapshot:` field exists on `AptRepository` (`apt.py:25,35`) but only Ubuntu uses it (`ubuntu.py:66,75,90`); Debian rewrites URLs instead.
- `mkosi latest-snapshot` (`__init__.py:4368-4369`, `debian.py:262-264`) queries `<mirror or snapshot.debian.org>/mr/timestamp` and prints the last entry.
- Bootstrap (`debian.py:125-220`): no debootstrap; merged-usr symlinks, `apt-get install ?essential ?architecture(amd64) base-files` with `Debug::pkgDPkgPm=1` to only download, `dpkg-deb --fsys-tarfile` extraction, then a real `apt-get install` of the essentials; `fixup_os_release` for sid.
- apt invocation (`apt.py:171-230`): `APT::Architecture(s)`, `Install-Recommends` from `WithRecommends=`, `Immediate-Configure=off`, `Dir::Cache=/var/cache/apt` (package cache dir), `Dir::State=/buildroot/var/lib/apt`, `DPkg::Options::=--root=/buildroot --force-unsafe-io --force-architecture --force-depends --no-debsig`, `pkgCacheGen::ForceEssential=,`, doc excludes via `--path-exclude` when `WithDocs=no`, proxy options; env `APT_CONFIG=/etc/apt.conf` (points `Dir::Etc` at the sandbox tree's `/etc/apt`, 120-134), `DEBIAN_FRONTEND=noninteractive`, `INITRD=No` when bootable (155-161). `policy-rc.d` denies daemon starts during install (254-262).
- `PackageDirectories=`: local repo built with `apt-ftparchive packages .` (`apt.py:290-297`) under `/repository` in the sandbox; `.deb`/`.ddeb` globs (62-64). `VolatilePackages=` installed after the cache point.
- Keyrings: `/usr/share/keyrings/debian-archive-keyring.gpg` must exist in the tools tree or host (`apt.py:137-143`); the Debian tools tree installs `debian-archive-keyring` (`resources/mkosi-tools/mkosi.conf.d/debian.conf`).
- Architecture mapping (`debian.py:237-259`); `is_kernel_package` = `linux-image-*` (267-268), used by `config_default_initrds`/`want_kernel`-style heuristics.
- `KernelModulesInitrd` compression special case for `sid`/`testing` (`__init__.py:1591-1597`).
- Backports: no setting; a `.sources` file in `mkosi.sandbox/etc/apt/sources.list.d/` (tundravm's current approach) is the supported way.

## 7. Integration options

### (a) `import mkosi` and call `run_verb(Args, [Config])`

What it buys: no argv marshalling; `Config` objects built with `dataclasses.replace(Config.default(), ...)` and validated by the same parsers; direct access to `build_image`'s pieces in theory.

What breaks:
- `run_verb` namespaces the calling process (`__init__.py:5134-5171`); tundravm would have to `os.fork()` (mkosi's own `fork_and_wait`, `run.py:195-235`) around every call, at which point it is a subprocess anyway. Under `sudo` or with `privilege="unshare"` the same constraints apply as today.
- `die()` -> `SystemExit`, logging to the root logger, `signal` handlers and `resource_path()` are `main()`'s business; replicating `__main__.py:31-49` is the minimum.
- `Config.default()`/`from_json` do a full parse that reads the host (`/proc` chdir, env vars, `detect_distribution`), so "pure" construction is impossible; and every `Config` field is required, there are no class-level defaults.
- Python floor: tundravm is 3.12-only, mkosi 3.9+: fine. No third-party deps on either side.
- Nothing is stable: 26 -> 27 removed/renamed functions (section 1.3), changed the privilege model, and changed `Config` JSON shape. Upstream gives no API promise; `AGENTS.md`/`docs/` say nothing about embedding.
- The `Context`/`build_image` internals (what you'd want for "just prune modules" or "just build the UKI") need the workspace, sandbox tree, keyring/metadata dirs that `run_verb` sets up (`setup_workspace` 4037-4054, `sync_repository_metadata` 4955).

Verdict: not worth it. The only in-process calls with a sane cost/benefit are read-only: `parse_config([...], resources=...)` to get the resolved `Config` (what `mkosi summary --json` does), `Config.from_json`/`to_dict` to validate or normalise JSON, and the pure `kmod.globs_match_*` helpers if tundravm ever wants to pre-validate `KernelModules=` globs. Each is a private symbol that can move in the next release; wrap them in one adapter module with a version guard.

### (b) Generate the tree and read back `mkosi --json summary`

What it buys: the fully resolved config (defaults, profiles, matches, includes, tools-tree path, subimage list with scopes applied) without privileges and without building; a second source of truth for tundravm's lockfile (`distribution`, `packages`, `KernelModules`, `SourceDateEpoch`, `Seed`, `Snapshot`, `ToolsTree*`); `cat-config` for a reviewable dump of what mkosi parsed; `mkosi dependencies` for host-package hints.

What breaks: it runs `mkosi.version`/`mkosi.rootpw` scripts (unsandboxed, `mkosi.1.md:2671-2683`), can trigger `--auto-bump`, may read history if `History=yes`, reads the host env; configure scripts are not applied; keys are mkosi-version dependent (unknown keys die on `from_json`, but reading the dict is fine). Normalisation as in section 2.3 is required before hashing.

Verdict: cheap and useful; do it in `lock`/`build --check` to detect drift between what tundravm thinks it emitted and what mkosi will use, and to record the resolved `Snapshot`/`ToolsTree` facts into the lockfile.

### (c) Keep shelling out; use `mkosi.config` types only for validation

What it buys: `SETTINGS_LOOKUP_BY_NAME` tells you whether a setting name exists in the pinned mkosi and in which section; `ConfigSetting.parse` validates values exactly as mkosi will (enums, paths, booleans, byte sizes, UUIDs); `Verb`, `OutputFormat`, `ArtifactOutput` enums for the emitter; `MinimumVersion=` enforcement for free.

What breaks: importing `mkosi.config` pulls in `mkosi.sandbox` (ctypes) and `mkosi.run`, harmless on Linux, but on macOS (Lima backend host) `import mkosi.config` still works since the ctypes calls are lazy (`sandbox.py` only calls `libc` inside functions); untested here. Version coupling again: `compat_names` and section moves (`[Host]` -> `[Runtime]`) are handled by mkosi's parser, so validating against the pinned version is exactly right, but `tundravm import` of foreign trees should tolerate older names (it does today via its own table).

Verdict: a small, contained win if mkosi is already a Python dependency (option d); otherwise not worth an import path that may be absent.

### (d) Pin mkosi as a Python dependency

What it buys: one toolchain line in `uv.lock` instead of "install mkosi v26 with pipx" in CI and `doctor`; `uv run mkosi`/`python -m mkosi` from tundravm's venv; `importlib.metadata.version("mkosi")` already preferred by `TV/toolchain.py:296-306`; the tools tree does the rest (host needs only python3 + apt/dpkg + user namespaces).

What breaks / to decide:
- Not on PyPI: `mkosi @ git+https://github.com/systemd/mkosi.git@v27.1` is a direct reference, which PyPI-published packages may not carry in `dependencies` (PEP 508 direct references are rejected by PyPI for uploaded distributions). tundravm itself is installed from git (`README.md:27`), so this only matters if tundravm is ever published to PyPI; alternatives are an optional-dependency group, a `[tool.uv.sources]` entry, or vendoring the 1.2 MB zipapp built by `tools/generate-zipapp.sh` (then `python3 vendored/mkosi.pyz`, which `python_binary()` handles when a tools tree is used).
- Version policy upstream: integer major releases roughly every 3-4 months (26: 2025-12-17, 27: 2026-09?, 27.1: 2026-09-28 per the tag), point releases rare, no deprecation period beyond warnings for renamed settings; `MinimumVersion=` is the only forward-compat tool. Pinning exact (`==27.1`) is the only sane choice; `27.*` does not exist as a concept on git refs.
- Privileges are unchanged: still user namespaces (or sudo), still `mkosi-sandbox`; nothing about pinning removes the Ubuntu AppArmor sysctls or the `/dev/kvm` group issue (`mkosi.1.md:3486-3498`).
- `sudo` + venv: `LocalLinuxBackend` passes `shutil.which("mkosi")` because sudo resets PATH (`local_linux.py:348-355`); with a venv install the absolute path is `<venv>/bin/mkosi`, fine, and `mkosi_python()` (190-200) already reads the shebang to find the interpreter for the pefile probe.
- Lima/nix backends currently get mkosi from nixpkgs inside the VM; a pip pin inside the VM means a venv there too, or dropping nix (the plan already proposes dropping nix and inprocess).

Verdict: do this (the plan's phase 0), with an exact git tag pin and `MinimumVersion=27.1` in the emitted `mkosi.conf`, plus a `summary --json` check that the running mkosi reports the pinned `__version__`.

### How mkosi's test-suite drives builds (the reference pattern)

`MK/tests/__init__.py`: `ImageConfig(distribution, release, debug_shell, snapshot)`; `Image.__enter__` picks a unique output dir under the cache dir and a unique machine name; `Image.mkosi(verb, options, args, stdin, check, env)` runs `python3 -m mkosi --debug *options verb *args` with `stdout=sys.stdout`; `build()` first runs `summary` with the same options (so parse errors surface before any privileged work), then `build` with `--distribution`, `--release`, `--snapshot` (pinned from `mkosi.local.conf` via `conftest.py:44-54`), `--kernel-command-line=...` (sets `systemd.unit=mkosi-check-and-shutdown.service`), `--force`, `--incremental=strict`, `--output-directory`; `boot()`/`vm()` pass `--ephemeral=yes --register=no --machine <name> --runtime-build-sources=no` and treat exit code 123 as success (the guest unit's `EXIT_STATUS`). CI runs the whole thing inside `mkosi box` (`ci.yml:33`), i.e. inside the tools tree sandbox. That is: argv + subprocess, summary before build, strict incremental, explicit snapshot, ephemeral boots, exit status from the guest. tundravm's `LocalLinuxBackend.command()` is already the same shape.

## 8. Recommendation

Keep the file tree as the contract and the `mkosi` CLI as the boundary (option d + b, with a thin c):

1. Pin mkosi 27.1 by git tag as a tundravm dependency; emit `MinimumVersion=27.1`; default `ToolsTree=default` so the host only needs python3, apt/dpkg and user namespaces. Record `ToolsTreeSnapshot`/`Snapshot` and the tools tree's `cache_manifest` facts in the lockfile instead of nixpkgs pins.
2. Run `mkosi summary --json` (and `cat-config`) from the generated tree before `build`; normalise and hash the `Images[]` dicts for drift detection; fail if `Seed`/`SourceDateEpoch`/`Snapshot` are unset for a release build; set `History=no`.
3. Keep tundravm's finalize-time module check and `depmod -a` (mkosi still skips depmod after pruning and ignores aliases); drop nothing from `kernel_modules.py` except the idea that it "reimplements the closure" (it does not). File the one-line depmod fix upstream.
4. Keep `measure/` entirely; mkosi has no RTMR/MRTD/PCR4-9 logic. Optionally add `SplitArtifacts=pcrs` to get ukify's PCR 11 policy digests as an extra evidence artifact.
5. `mkosi vm` can replace `testing/_boot.py` only for non-TDX boots, after adding a notify-socket exit-status unit (or `ForwardJournal=`) to the test image; keep `deploy/qemu.py` for TDX until `Firmware=linux` + `QemuArgs=-bios TDVF ...` is verified on a TDX host, and consider an upstream `Firmware=tdx` patch (small: skip pflash, add `-bios`, `-object tdx-guest`, `confidential-guest-support`, `kernel-irqchip=split`).
6. Use `mkosi.images/` + `Dependencies=` for the qemu/azure/gcp disk wrappers, `mkosi.profiles/` for `dev`, `mkosi.conf.d/` with `[Match] Image=`/`Profiles=` for shared drop-ins, `mkosi.sandbox/` for apt sources, `mkosi.uki-profiles/` if more than one cmdline per UKI is needed. Do not use `--include` as a substitute for `--directory` because subimages are only discovered from the config directory.
7. Do not call `run_verb`/`build_image` in-process; if any `mkosi.*` import survives, confine it to one adapter module (`parse_config`, `Config.from_json`, `SETTINGS_LOOKUP_BY_NAME`, `kmod.globs_match_module`) guarded by the pinned version string.
